# Chatwoot как каноническая платформа разговоров

**Статус:** предложено к реализации

## Цель

Сделать Chatwoot единственным постоянным хранилищем продукта: каналов, истории
сообщений, контактов, очереди, передачи дежурной и состояния сценария. Telegram
становится только транспортом этого разговора. Python-сервис остаётся
канал-независимым и stateless Agent Bot: он отвечает за product policy, вызовы
Qwen, детерминированную маршрутизацию по безопасности и интеграцию с каталогом
помощи, но не хранит собственные данные.

Первый канал — Telegram. WhatsApp и веб-чат в будущем будут inbox-ами Chatwoot
с тем же контрактом Agent Bot; их добавление не должно требовать нового
хранилища разговоров или второй реализации policy.

## Решения и инварианты

1. Chatwoot хранит каждое тело сообщения, вложение, контакт, назначение,
   состояние сценария и видимое пользователю состояние разговора. Приложение
   не держит вторую копию истории или иной пользовательской переписки.
2. У Python Agent Bot нет собственной базы данных. Он взаимодействует с
   Chatwoot только через его API и никогда не пишет напрямую в его PostgreSQL.
   Всё, что должна видеть дежурная, остаётся в Chatwoot: в сообщениях, тегах,
   атрибутах и внутренних заметках.
   В development- и test-контурах PostgreSQL запускается вместе с Chatwoot в
   Podman Compose. В production Chatwoot подключается к отдельному Yandex
   Managed PostgreSQL.
3. В тестовом контуре данные пока не удаляются автоматически. Политика сроков
   хранения и сквозное удаление — отдельный техдолг, который нужно закрыть до
   внешнего запуска сервиса.
4. Chatwoot становится клиентом Telegram Bot API. После переключения
   существующий aiogram polling-процесс исключается из production-пути
   сообщений.
5. Python-сервис остаётся окончательной инстанцией, решающей, может ли Qwen
   ответить. Статус, назначение или действие в панели Chatwoot не обходят
   policy безопасности.
6. Сохраняется текущее продуктовое правило: прямой запрос человека или
   эскалация по безопасности сразу передаёт владение ответом дежурной команде;
   AI молчит, пока кейс явно не вернут боту.
7. Текущие production-разговоры автоматически в Chatwoot не импортируются.
   Переключение создаёт новую границу истории и не копирует старые
   чувствительные тестовые данные в новую систему.

## Целевая топология

```text
Telegram / будущий канал
          |
          v
 Chatwoot inbox + PostgreSQL, Redis, каноническая история и хранилище вложений
          |                         ^
          | событие Agent Bot        | Messages / assignment / labels API
          | Agent Bot                |
          v                         |
 stateless Python Agent Bot --------+
          |
          v
 Yandex AI Studio
```

В Chatwoot создаётся один аккаунт и один Agent Bot фонда. Каждый канал — это
отдельный inbox. Дежурная команда получает доступ только к релевантным inbox-ам.

Python-сервис предоставляет HTTPS-приёмник событий Agent Bot. Chatwoot
вызывает его для входящей пользовательской активности. Сервис читает историю
разговора через application API Chatwoot, маскирует её для модели в рамках
действующей PII-границы, разрешает ход по policy и добавляет ответ в тот же
разговор Chatwoot от имени Agent Bot.

Перед каждым ходом сервис заново читает назначение, статус и атрибуты разговора
из Chatwoot. Поэтому действие сотрудницы в панели Chatwoot сразу становится
источником истины и не требует синхронизации второй базы.

## Кто отвечает в разговоре

У разговора в Chatwoot есть только два режима, записанные в custom attribute
`reply_owner`:

| `reply_owner` | Настройка разговора в Chatwoot | Кто отвечает |
| --- | --- | --- |
| `bot` | назначен Agent Bot, обычно `pending` | Python Agent Bot |
| `human` | назначена дежурная команда или конкретная сотрудница, обычно `open` | только человек |

Новый разговор без назначения человека создаётся с `reply_owner = bot`. Рядом
в custom attributes хранится `context_epoch`, а приватная заметка Agent Bot
служит маркером начала этой эпохи.

Прямой запрос на разговор с человеком и любая эскалация сразу ставят
`reply_owner = human`, назначают разговор дежурной команде в Chatwoot и не дают
модели отвечать. Не нужно различать «команде уже передали» и «сотрудница уже
взяла кейс»: в обоих случаях бот молчит.

Возврат кейса боту — явное действие: снять назначение человека, назначить
Agent Bot и поставить `reply_owner = bot`. Одного изменения статуса недостаточно.

`open`, `pending` и `resolved` — нативные статусы Chatwoot, нужные для его
очереди и интерфейса. Это не дополнительные состояния бота. Если новое входящее
сообщение переоткрывает `resolved` разговор, владельца ответа определяет его
назначение: человек при активном назначении, иначе бот.

Перед вызовом LLM и перед публикацией ответа сервис повторно проверяет
`reply_owner`, статус и актуальное назначение в Chatwoot. Поэтому назначение
дежурной всегда выигрывает у уже запущенного ответа модели.

## Обработка сообщений и событий

1. Chatwoot принимает пользовательское сообщение из любого inbox-а и записывает
   его в собственную историю.
2. Он отправляет событие `message_created` Agent Bot в Python-приёмник.
3. В текущем v4.12.1 приёмник аутентифицируется защищённым URL и использует
   message ID для deduplication. После перехода на релиз с поддержкой Agent
   Bot signatures приёмник проверяет HMAC, timestamp и идентификатор доставки.
   Один экземпляр Agent Bot последовательно обрабатывает события каждого
   разговора в памяти; после перезапуска состояние не восстанавливается из
   отдельной БД.
4. Он читает актуальный разговор из Chatwoot и игнорирует не-пользовательские,
   устаревшие события, разговоры со значением `reply_owner = human` и разговоры,
   назначенные дежурной команде или сотруднице.
5. Он получает активную историю из Chatwoot, отсекает сообщения до последней
   приватной заметки текущего `context_epoch`, параллельно запускает две
   существующие диагностики и разрешает детерминированную policy.
6. До запуска модели он ищет в истории исходящее сообщение Agent Bot с
   `content_attributes.bot_turn_key`, равным ключу текущего входящего сообщения.
   Найденный ключ означает, что ход уже обработан и повторный ответ не нужен.
7. Перед публикацией сервис повторно читает разговор. В исходящее сообщение он
   записывает тот же `bot_turn_key` через `content_attributes`. При таймауте
   повтор начинается с чтения истории Chatwoot, а не со слепой повторной отправки.
8. Результат с передачей человеку или эскалацией безопасности сначала меняет
   `reply_owner`, приоритет, теги, назначение команде и статус через API
   Chatwoot. Если это не удалось, сервис действует fail-closed: бот не отвечает.

## Данные в Chatwoot

Все постоянные данные находятся в Chatwoot:

- сообщения, вложения, контакты, каналы, назначения, статусы и теги;
- `reply_owner` и `context_epoch` в custom attributes разговора;
- маркер `/clear` и записи об эскалации в приватных заметках;
- выбранная помощь и данные, нужные дежурной, в атрибутах, тегах и заметках;
- `bot_turn_key` в `content_attributes` исходящего сообщения для безопасной
  обработки повторной webhook-доставки.

`/clear` увеличивает `context_epoch` в Chatwoot и публикует приватную заметку.
Полная история остаётся видна дежурной, но для следующего контекста LLM подходят
только сообщения новой эпохи.

## Техдолг: срок хранения и удаление

В текущем тестовом MVP не запускается ни worker удаления, ни TTL-задача.
Переписка, вложения и резервные копии Chatwoot остаются доступны, пока их не
удалят вручную в рамках отдельной операционной процедуры.

До внешнего запуска нужно отдельно согласовать срок хранения и реализовать
проверяемое сквозное удаление: разговора Chatwoot, вложений и резервных копий.
После этого в документ вернутся автоматический worker, проверка удаления и тест
просроченной webhook-доставки.

В первоначальном text-only MVP policy Agent Bot отклоняет вложения. Перед
включением медиа отдельный acceptance test должен подтвердить требуемое
поведение выбранного Active Storage backend.

## Техдолг: отложенный контакт

Автоматический вопрос «как вы?» через заданное время не входит в stateless MVP.
Перед его добавлением нужно проверить, позволяет ли выбранная версия Chatwoot
выполнить сценарий собственной автоматизацией. Если нет, это будет отдельная
осознанная причина добавить небольшой планировщик с постоянным хранилищем.

## Границы безопасности

- Chatwoot и Agent API взаимодействуют по TLS и, где доступно, по приватной
  сети. Test-контур временно закреплён на Chatwoot v4.12.1: его Agent Bot
  webhook ещё не имеет HMAC-подписей, поэтому URL содержит отдельный
  высокоэнтропийный secret и delivery deduplicate выполняется по message ID.
  Когда self-hosted Agent Bot в поддерживаемом исправленном релизе снова
  доступен, обязательными будут HMAC Chatwoot, допустимое расхождение времени
  и ID доставки; API уже умеет этот режим.
- Токен Agent Bot, административный токен Chatwoot и webhook secret различны.
  Они хранятся в production secret-файлах с ограниченными правами и никогда не
  логируются и не попадают в исходный код.
- Agent API принимает только небольшой webhook surface; панель Chatwoot
  защищается отдельно, а дежурные получают роль `agent`, не `administrator`.
- Chatwoot Captain выключен. Единственный поставщик LLM в продуктовом пути —
  Qwen в Yandex AI Studio.
- Текст истории, написанный пользователем, является недоверенным вводом для
  модели. Действующие границы prompt injection, курируемых знаний и policy
  сохраняются.

## Топология развёртывания

Для development и тестов одной VM достаточно. В одном Podman Compose-проекте
работают:

- приложение Chatwoot, worker, Redis, PostgreSQL и text-only storage;
- один stateless Python Agent Bot без собственной базы и persistent volume;
- reverse proxy с двумя HTTPS hostname.

Локальный PostgreSQL нужен только этому development-контуру и хранит данные в
именованном Podman volume. Agent Bot не делит его таблицы, учётные данные или
Redis и не получает прямой доступ к внутренней базе.

Production-контур использует те же образы Chatwoot и Agent Bot, но не содержит
контейнера PostgreSQL. Rails и Sidekiq получают FQDN, порт `6432`, имя базы и
учётные данные Yandex Managed PostgreSQL через `POSTGRES_HOST`, `POSTGRES_PORT`,
`POSTGRES_DATABASE`, `POSTGRES_USERNAME` и `POSTGRES_PASSWORD`. Кластер
Managed PostgreSQL размещается в той же VPC без публичного доступа; для
доступности в нём должно быть не менее двух хостов в разных зонах.

Для образа Chatwoot всегда фиксируется конкретный patched release tag, никогда
не используется `latest`.

## Переход в Managed PostgreSQL

Перед первым production-запуском пользователь создаёт отдельные production
кластер, базу и пользователя в Yandex Managed PostgreSQL. Если зафиксированный
релиз Chatwoot потребует `pgvector`, расширение включается через настройки
Managed PostgreSQL до запуска миграций.

Затем deployment выполняет миграции Chatwoot в новой production-базе и проводит
smoke check. Тестовые разговоры из локального PostgreSQL не мигрируются: это
сохраняет чистую границу между тестовыми и реальными данными. Перенос данных
между контурами возможен только как отдельная явно согласованная операция.


## Rollout и rollback

1. Построить channel-neutral stateless Agent Bot и HTTP-приёмник под тестами;
   действующий Telegram polling остаётся live-путём.
2. Поднять изолированный test account Chatwoot и отдельного Telegram test bot.
   PostgreSQL в этом контуре запускается локально вместе с Chatwoot.
   На синтетических данных проверить входящий текст, ответ бота, кнопки,
   `/clear`, эскалацию безопасности, захват человеком, возврат боту и
   повторную доставку одного webhook-события.
3. После создания пользователем Managed PostgreSQL выложить проверенные Agent
   Bot и Chatwoot в production, подключив Rails и Sidekiq к новой managed-базе,
   но пока не назначать текущий Telegram token Chatwoot.
4. В короткое согласованное окно переключения остановить старый aiogram-сервис,
   настроить Telegram inbox Chatwoot с действующим token, привязать Agent Bot и
   провести live smoke checks. Только после этого отметить новую версию активной.
5. Rollback выполняется явно: отвязать Agent Bot, убрать Telegram inbox webhook,
   восстановить старый сервис бота и его token-конфигурацию. Старая история
   остаётся в прежнем сервисе; новая pilot-история Chatwoot обратно не копируется.

## Критерии приёмки

- Синтетическое сообщение через Telegram test bot ровно один раз появляется в
  Chatwoot, вызывает не более одного хода Agent Bot и получает один ответ.
- Все текущие действия меню работают как Telegram-кнопки через Chatwoot.
- Событие безопасности создаёт видимый high-priority кейс, маршрутизируется
  дежурной команде и не даёт боту отвечать после назначения человека.
- Ответ дежурной доходит до Telegram ровно один раз и виден в Chatwoot как
  ответ этого агента.
- `/clear` исключает предыдущие сообщения из следующего вызова модели, не
  удаляя историю, доступную дежурной.
- Повторная доставка и перезапуск Agent Bot не создают второй видимый ответ на
  одно входящее сообщение: это проверяется по `bot_turn_key` в истории Chatwoot.
- В тестовом контуре нет автоматического удаления. Его сквозная проверка —
  техдолг, обязательный перед внешним запуском.
- Недоступность Chatwoot не создаёт внешнего состояния вне Chatwoot; ошибки
  наблюдаемы и повторяемы без дублирования ответов.
- Development использует локальный PostgreSQL в Compose, а production — только
  отдельную Yandex Managed PostgreSQL базу; тестовые разговоры между ними не
  переносятся.
