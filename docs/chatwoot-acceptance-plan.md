# План приёмки интеграции Chatwoot

Дата локальной проверки: 2026-10-03. Область: Chatwoot API, Agent Bot и рабочее место специалистки. Telegram transport, реальные обращения, реальные сертификаты и изменение production-настроек не входят в этот план.

## 1. Что именно считается проверенным

Разделяем три независимых результата:

1. **Локальная регрессия текущей реализации** — заглушки Chatwoot, модели и хранилища; подтверждает программные контракты, но не доставку, права и UI.
2. **Live Chatwoot acceptance** — новый синтетический контакт и разговор в `Channel::Api`; подтверждает цепочку Chatwoot → webhook → Agent Bot → Chatwoot и выбранные действия сотрудницы. Выполняет основной агент, не автор этого плана.
3. **Приёмка нового сценария** — `docs/nevidimy-bot-scenario-final.html`, структурно 57 экранов. Это отдельная матрица требований; текущее прохождение smoke не означает, что сценарий реализован целиком.

Статусы ниже: **L** — покрыто локальным тестом; **S** — уже входит в live smoke, но требует успешного текущего запуска; **M** — дополнительная ручная/интеграционная проверка; **P** — требование нового сценария, покрытие реализации ещё не подтверждено. Статус S сам по себе не означает live PASS.

## 2. Изоляция и ограничения

- Использовать только отдельный API inbox `Техническая проверка интеграции`, без external delivery webhook, с привязанным Agent Bot.
- Имя синтетического контакта: `Техническая проверка — не обращение`. Для каждого suite — новый контакт и разговор с уникальным `run_id`; не переиспользовать чужие ID.
- Перед записью проверить account, inbox, `Channel::Api`, имя контакта и принадлежность conversation текущему прогону. При несовпадении остановиться до отправки.
- Публичный `incoming` создаётся от синтетического клиента; публичный `outgoing` и private note сотрудницы — через её проверенную авторизованную identity; ответ бота — identity Agent Bot. Нельзя подменять тип отправителя только текстом сообщения.
- Не менять роли, ACL, членство команд, общие macros/filters, URL, secrets или runtime-конфигурацию ради теста. Их отсутствующее состояние — отдельный блокер, а не разрешение на изменение.
- Назначение команды может вызвать реальные внутренние уведомления. Допустимы только согласованные тестовые действия с явно помеченным разговором; массовые/повторные уведомления не нужны.
- Не нажимать подтверждение выдачи сертификата в live-контуре, если это может расходовать общий пул. Пустой общий пул не имитировать удалением остатков.
- Не запускать provider fault injection, перезапуск сервиса, изменение часов ОС или production БД для гонок/таймеров. Для этого нужен отдельный разрешённый тестовый контур.
- Закрыть только созданные тестовые разговоры в `resolved`; сохранить их для аудита. Не удалять контакты и историю как «очистку».
- В отчёте: ID, состояние, счётчики, timestamp, `run_id`, статус проверки. Без токенов, тел переписок, сертификатов и данных реальных людей.

## 3. Как запускать имеющийся live smoke

Основной агент конфигурирует официальный Chatwoot CLI. Поддерживаемый вход:

```sh
just chatwoot-test-live all
just chatwoot-test-live dialogue
just chatwoot-test-live queues
```

`scripts/chatwoot_acceptance.py` использует CLI transport, создаёт свежий разговор на каждый suite, проверяет тестовый inbox, ограничивает целевые записи, вызывает существующие smoke и сохраняет обезличенный отчёт `.runtime/chatwoot-tests/<run_id>.json`. Итоговый PASS требует также успешного завершения cleanup. Нельзя заменять этот вход ручным вызовом старого smoke с произвольным conversation ID.

`dialogue` использует `scripts/chatwoot_live_smoke.py`: старт, меню, back, текущую модель/кнопки, системную информацию, handoff notification, продолжение бота, clear, human takeover и explicit return.

`queues` использует `scripts/chatwoot_queue_smoke.py`: каталог команд, маршрутизацию, уведомление, native macros, видимое назначение, возврат боту и фильтр команды. Проверка фильтра должна находить именно ID текущего тестового разговора, а не только успешный HTTP-ответ/словарь.

Ограничения обоих suite: они не проверяют внешний мессенджер, весь UI под разными ролями, полноценную выдачу сертификатов, отложенные анкеты и весь новый HTML. Текст системной информации о транспортной цепочке не доказывает работу какого-либо транспорта.

### Видимость и фильтры: отдельный обязательный шаг

Нужны минимум две синтетические conversation разных очередей и существующая разрешённая identity специалистки. Проверить списки «Мои», «Не назначены», командную папку и прямое открытие ID. После назначения/переноса/снятия/закрытия проверить актуальный статус и отсутствие устаревшего попадания в неправильный фильтр. Перезагрузить UI и повторить чтение.

Фильтр списка — не ACL. Отсутствие разговора в папке не доказывает запрет прямого доступа; видимость коллегой в той же команде не обязательно ошибка. Сначала зафиксировать ожидаемую матрицу прав организации. Если доступна только admin identity, эту часть оставить **NOT VERIFIED**, не выдавать за успешную ролевую проверку.

### Доказательство «бот молчит»

Сравнить число bot replies по новым incoming ID до/после, дождаться обработки ownership event и ограниченного контрольного окна. Короткое отсутствие ответа — только наблюдение за этим окном. Гонки и гарантии после рестарта подтверждать локальными детерминированными тестами/отдельной управляемой интеграцией, не бесконечным ожиданием production.

## 5. Сертификаты без расходования реального пула

**Сейчас безопасно:** локальные InMemory/stub inventory tests; локально сгенерированные тестовые PDF; live просмотр меню/описания без подтверждения выдачи. Generic `Channel::Api` не является гарантией test-only inventory.

Для полноценной live выдачи требуется отдельное доказательство изоляции test pool, test recipient и объектов хранения от реального инвентаря. До этого все live positive issuance cases — **BLOCKED BY ISOLATION**, а не «пройдены по mock». Не импортировать, не сбрасывать и не истощать production inventory.

| ID | Проверка | Ожидаемый результат / граница |
|---|---|---|
| CERT-01 | Четыре категории: продукты, лекарства, проживание, детские товары | Верный pool/document mapping; положительная выдача только после подтверждения и только тестового документа |
| CERT-02 | Повтор callback/event, новый разговор того же получателя, clear и смена категории | Не появляется второй entitlement/сертификат; identity стабилен внутри account и разделён между account |
| CERT-03 | Истёкший, отсутствующий или уже выданный документ | Не выдаётся невалидный/чужой документ; пустой пул не потребляет entitlement; доступен корректный дальнейший путь |
| CERT-04 | PDF → инструкция/follow-up | Сначала документ; follow-up не обгоняет отправку; message ID сохраняется для delivery bookkeeping |
| CERT-05 | `sent/delivered/read/failed`, дубли delivery event и ошибки upload/send | Состояние меняется по связанному message ID, без утечки содержимого; не заявлять внешнюю доставку по одному accepted API request |
| CERT-06 | История, notes, отчёты и модель | Сертификат/код не попадает в отчёт и будущий model context; masking сохраняется после clear/повторного открытия |
| CERT-07 | Юридическая/психологическая помощь после исчерпания сертификатного лимита | Несертификатная помощь остаётся доступна; текст не обещает вторую выдачу |

Текущие локальные тесты подтверждают части CERT-01–07, но не все отказы, конкуренцию нескольких процессов, реальную БД inventory и внешнюю доставку. PDF mock и generic Chatwoot message не доказывают успешное получение документа клиенткой.

## 7. Отложенные опросы: requirements pending

В текущем Chatwoot adapter workflow восстанавливается в InMemory store, а заявки сохраняются private notes. Наличие callback `followup:*` или общего доменного follow-up теста **не доказывает** работающий persistent scheduler в Chatwoot. Новый блок нужно принимать отдельно после реализации.

| ID | Время / событие | Что проверить детерминированными часами, затем в изолированной интеграции |
|---|---|---|
| TIME-01 | Помощь оказана → 4 дня; допустимое окно 10:00–20:00 | До due ничего нет; один нужный вопрос в окне; после перезапуска job не теряется и не дублируется |
| TIME-02 | Одновременно сертификат и консультация | Блок 5 спрашивает о сертификате; консультация имеет отдельную оценку блока 7; два триггера не создают одинаковый опрос |
| TIME-03 | Только консультация, с учётом состоялась ли она к моменту блока 5 | Выбрана правильная версия вопроса; сертификатные вопросы `s51/s511` не показываются |
| TIME-04 | Нет ответа → ещё 2 дня | Одно напоминание `s59`, только днём и пока сертификат действует; затем тишина, даже после рестарта/retry |
| TIME-05 | Завершение консультации → 1–2 часа | Один `s7`; если консультация закончилась вечером — следующий день после 10:00; не запускать от одного лишь назначения/отправки запроса |
| TIME-06 | После блока 7 пользовательница приходит в ветку итоговой обратной связи | Кнопки, ведущие обычно к `s6`, завершают разговор без второй анкеты |
| TIME-07 | Ответ, finish, human takeover, новый запрос, истечение сертификата до due | Правила отмены/переноса/паузы явно согласованы; отсутствуют неподходящие автоматические сообщения |
| TIME-08 | Дубли completion event, delayed/out-of-order worker, несколько workers | Один survey instance на предмет помощи, монотонное состояние; ответы не записываются в чужую/старую анкету |
| TIME-09 | Повторный запрос `s561` и негативная оценка `s721` | Один связанный запрос/сигнал нужной получательнице; retry не дублирует уведомления; оригинальная заявка сохранена |
| TIME-10 | Граница 09:59/10:00/19:59/20:00, полночь, разные часовые пояса | Отправка соответствует согласованной timezone и включительности границ; системные часы production не меняются |

Уточнения пользователя: «Консультация завершена» закрывает разговор и возвращает владение боту; новое входящее получает ответ. Опрос — через два часа от окончания встречи с переносом в окно [10:00, 20:00) МСК. Встречу можно запланировать на будущее отдельным макросом; закрытие чата не запускает опрос. Проверять перенос/отмену, неоднозначную заявку, неверную дату, повтор webhook, рестарт и отсутствие повторной отправки. Блок 5 — через 96 часов, для PDF от подтверждённой доставки. При активном специалисте опрос ждёт; И4 — один раз через час после первого меню, с отменой при активности или передаче человеку; И9 — после 24 часов тишины. Эти детали требуют отдельных проверок, базовый live smoke их не доказывает. Подтверждённые решения находятся в `scenario-update-review.md`, локальная реализация — в `scenario-runtime.md`.

## 8. Негативные и устойчивость

- Пустое/слишком длинное сообщение, unsupported attachment, неизвестный callback, кнопка старого экрана, повторный клик: контролируемый результат без падения, новой лишней заявки и смены чужого owner.
- Private incoming, activity, собственное сообщение Agent Bot, irrelevant event: не запускают рекурсивный ответ.
- Повтор webhook ID и повтор текста с новым message ID различать: первый дедуплицируется, второй — новый клиентский ход.
- Отказ модели/timeout/недоступность маршрутизатора: безопасный детерминированный путь, без загрузки дополнительных raw safety fixtures и без попыток обхода provider filter.
- Chatwoot 401/403/404/429/5xx, сетевой timeout и частичный успех send: не публиковать credentials/полные response bodies; повторять только идемпотентно и в рамках test conversation.
- Падение между изменением состояния и отправкой, восстановление service instance, одновременный human takeover: отсутствие late bot reply и повторного side effect.
- Неизвестный account/conversation/recipient в event: никакого cross-account ответа, выдачи или изменения ownership.
- Установка legacy/signed webhook mode — отдельная конфигурационная приёмка; negative tests не должны менять production security mode.

Наличие строки в этом разделе означает требование проверки, а не существующий автоматический тест на каждый случай.

## 10. Критерий завершения

Текущий Chatwoot baseline принимается после локальной регрессии, успешного свежего `dialogue/queues` отчёта, проверки собственных test conversation ID и отсутствия нежелательных side effects. Ролевую видимость и клиентскую невидимость private notes либо проверить отдельно, либо явно оставить непроверенными.

Полный новый сценарий принимается только после связывания всех 57 screen ID с runtime-переходами, покрытия таймеров и инвентаря в изолированном контуре и прогона соответствующих negative cases. До этого итоговая формулировка: **«Текущая интеграция проверена в перечисленных границах; новый сценарий покрыт не полностью»**.

В финальном live отчёте указать: run ID/путь, версии CLI и проверяемого кода, account/inbox и созданные conversation ID, PASS/FAIL/BLOCKED/NOT VERIFIED по suite, длительность/окно наблюдения, cleanup, ограничения ролей, неизменность реального inventory и отсутствие Telegram transport проверки.
