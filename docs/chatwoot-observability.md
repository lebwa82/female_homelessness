# Метрики запросов Chatwoot

Backend экспортирует Prometheus-метрики по `/metrics` на том же **внутреннем
HTTPS-порту**, что webhook. Отдельный HTTP-сервер или публичный порт не нужен.
Внешний reverse proxy Chatwoot этот адрес не публикует. В режиме без внутреннего
TLS endpoint нельзя выставлять наружу.

Используется официальный `prometheus-client`; зависимости закреплены в `uv.lock`.
Метрики живут в памяти одного процесса и сбрасываются при его замене. Для истории
нужен Prometheus, для графиков — Grafana. Наличие `/metrics` само по себе не означает,
что сборщик и дашборд уже запущены.

## Что измеряется

| Семейство | Что означает |
| --- | --- |
| `nevidimy_chatwoot_api_request_duration_seconds` | Все исходящие запросы к Chatwoot, включая служебные события и планировщик |
| `nevidimy_http_request_duration_seconds` | Входящие HTTP-запросы backend: webhook, health и прочие; не полное время ответа бота |
| `nevidimy_event_processing_duration_seconds` | Обработка одной попытки входящего сообщения; результат `replied`, `silent` или `error` |
| `nevidimy_event_queue_age_seconds` | Возраст входящего события Redis в начале попытки; включает ожидание повторов |
| `nevidimy_event_stage_duration_seconds` | История, сценарий, проверки владения, запись состояния и ответа |
| `nevidimy_first_reply_created_seconds` | До записи первого публичного ответа, начиная с обработки; **без доставки Telegram** |
| `nevidimy_event_api_requests` | Число исходящих запросов к Chatwoot в одной попытке обработки |

Суффикс `_count` даёт число наблюдений, `_sum` — сумму, `_bucket` — распределение.
Количество запросов в секунду вычисляется через `rate(..._count[5m])`; отдельные
дублирующие счётчики для тех же наблюдений не нужны.

### Быстрые сценарные кнопки

`CHATWOOT_FAST_BUTTONS` включает компактное чтение и условную атомарную запись
на существующих авторизованных API-действиях Chatwoot. Python рассчитывает тот
же сценарий в буфере без внешних эффектов. Chatwoot под блокировкой повторяет
проверки версии, назначения специалистке, позднего ответа и дубликата, затем
сохраняет workflow и исходящий Message одной транзакцией. Только явно разрешённые
внутренние поля workflow не порождают повторный `conversation_updated`.

При объявленной native capability `private_notes_v1` в ту же транзакцию входят
сценарные заявки, их receipts и до четырёх приватных заметок с ключами
`scenario:<24 hex>` / `scenario-alert:<24 hex>`. Существующие receipts читаются
через native coder во всём разговоре, включая записи до текущего входящего.
Повтор или сбой создания любой заметки/ответа не оставляет частичных записей.
Без этой capability план с заметками возвращается к прежнему обработчику до POST.

Только явный no-write ответ `409 {outcome: "conflict", reason: "stale_version"}`
разрешает один новый snapshot и полный пересчёт в новом буфере. Старые заметки,
состояние и ответ не переиспользуются. Второй конфликт или generic 409 сохраняет
прежний fallback; timeout/5xx/неоднозначный результат POST не разрешает ни его,
ни дополнительную отправку. Native duplicate-before-version и guards не ослабляются.

Файлы, уведомления, смена назначения и другие неподдерживаемые эффекты переходят
на прежний обработчик **до** внешних действий. Неизвестный результат POST не
считается разрешением отправить ещё один ответ. Нативные callbacks доставки
остаются после commit: сохранённый Message сам по себе не доказывает Telegram-доставку.

Ключ ответа читается через native `store` coder Chatwoot: установленная версия
хранит `content_attributes` как JSON-строку внутри JSON-колонки, поэтому прямой поиск
JSON-ключа может пропустить дубликат. Проверяется только исходящая метаинформация
после входящего ID, без загрузки текста истории.

`tests/timeweb_atomic_turn_live_probe.rb` проверяет native авторизацию, откат,
дубликаты и настоящие блокировки БД. Запускать только с подготовленным уникальным
API-inbox и acceptance-маркером, никогда на клиентском разговоре. Реквизиты
передаются через закрытое окружение. Задания перехватывает тестовый адаптер:
такой прогон не подтверждает скорость production или доставку Telegram.

Лог `nevidimy_atomic_turn_timing` разделяет native builder, after-commit callbacks
и SQL (`schema`, `cached`, `uncached`) внутри atomic-create. В нём только
фиксированные числовые поля, HTTP-статус и ID исходящего сообщения; SQL, binds,
текст и параметры не записываются. Это время тела action без предшествующей
авторизации и сети, а не end-to-end latency. Вложенные spans нельзя слепо суммировать.

Внутри `dispatch_create_events` отдельно видны `ui_message_created`,
`ui_conversation_updated`, `bot_message_created`, `bot_conversation_updated`.
Это вложенные замеры штатных listeners, а не перенос работы или изменение
порядка событий. `nevidimy_telegram_input_timing` измеряет выполнение нативного
Telegram job с теми же SQL/CPU/GC-счётчиками и числовым `incoming_message_id`;
ожидание очереди в него не входит. Аргументы job, текст, URL и исключения не
читаются для логирования. Тайминги root/job и вложенных listeners пересекаются.

Опциональные `thread_cpu_ms`, `process_gc_ms`, `process_allocated_objects` помогают
отделить CPU от ожидания. CPU относится к текущему thread; GC и allocations —
дельты всего процесса и при параллельных запросах включают работу других threads.
Недоступные или некорректные счётчики пропускаются, настройки GC не меняются.

Для восстановления waterfall у native timing event есть `started_at_ms` и
`finished_at_ms` (Unix milliseconds). В `timeline` сохраняется не более 64
вызовов из фиксированного списка spans: имя `span`, смещения `start_ms` /
`end_ms` относительно начала root scope, `sql_count`, `sql_elapsed_ms` и,
если доступен, `thread_cpu_ms`. Переполнение учитывается в `timeline_dropped`.
Смещения и длительности основаны на monotonic clock; абсолютное время нужно
только для связи с другими процессами. Записи упорядочены по началу.

Вложенные spans, их SQL и CPU inclusive: их **нельзя складывать** с родителем.
Разность wall time и thread CPU — не доказанное I/O: туда могут входить
планирование, ожидание блокировок/GVL и другие паузы. Текст SQL, параметры,
сообщения, URL, headers и credentials в эти поля не попадают.

Один trace сопоставляется по техническим incoming/outgoing message IDs с
ingress timestamp, существующими enqueue/start/finish логами ActiveJob и
`nevidimy_telegram_send`. `Message.created_at` — момент создания строки, а
не доказательство завершённого commit/callbacks или постановки доставки.
Поэтому интервал от этой метки до Telegram accepted нельзя целиком называть
очередью. Сравнивать следует одну и ту же границу для одного события;
сумма медиан отдельных этапов не является реальным waterfall.

Нативный Telegram sender переиспользует проверенные HTTPS-соединения через
существующий прокси, без автоматического повтора неоднозначного POST. Его
content-free лог `nevidimy_telegram_send` отдельно показывает `http_elapsed_ms`,
`send_elapsed_ms` и `source_to_accepted_ms`. Последняя величина начинается до
подтверждения callback в ingress и заканчивается получением внешнего message ID;
это не время отображения на телефоне. Без доверенной входящей метки она `null`.

В lifecycle `startup` Sidekiq готовятся два соединения с теми же настройками
HTTParty/proxy/CA, что у native POST. Один фоновый поток в этом же PID поддерживает
их token-free `HEAD /` каждые 10 секунд и готовит замену до предельных 300 секунд.
Redirect не выполняется, каждый HEAD ограничен deadline; busy lease не забирается,
а при ошибке прогрева штатная отправка остаётся доступной. В Rails preload поток
не запускается, `quiet/shutdown` его останавливают. Предел общего пула — четыре lease.

`pool_checkout_ms` измеряет подбор/аренду сокета, `connection_reused` сверяет
идентичность реального Net::HTTP socket, а `tls_setup_ms` включает TCP/CONNECT/TLS
при явном открытии. При скрытом pre-write reconnect значение setup остаётся `null`,
а не ложным нулём. Проверка в отдельном canary не доказывает прогрев рабочего
Sidekiq: после выкладки нужны его startup event/PID и живой sender trace.

Дополнительные поля checkout разделяют подготовку ключа (`pool_key_ms`),
первое ожидание mutex (`pool_mutex_wait_ms`) и ожидание lease через condition
variable, включая повторное получение mutex (`pool_lease_wait_ms`).
`pool_idle_closed` — число удалённых idle-соединений, `pool_checkout_cpu_ms` —
thread CPU за весь checkout. CPU пересекается с wall-time и не складывается
с ним; эти поля не превращают весь checkout в «ожидание свободного сокета».
Их наличие в коде не доказывает активацию на рабочем Sidekiq.

В transport добавлены четыре более узких таймера (само наличие кода не
подтверждает их активацию в production): `raw_request_ms` охватывает вызов
Net::HTTP после checkout/setup; `request_to_headers_ms` — от этого начала до
входа в уже существующий response callback, включая запись запроса и ожидание
заголовков. `response_block_ms` — время исходного callback, `response_tail_ms` —
оставшаяся часть вызова после его входа, исключая callback. Последние три части
не пересекаются и складываются в raw request; это не чистые сетевые RTT.
Обычный HTTParty читает тело после callback (tail), streaming caller может
читать его внутри callback. Без исходного callback новые блоки не добавляются,
поэтому известен только raw timer. Ошибка измерения даёт `null`, не сбой доставки.
Нативный lazy JSON parse выполняется после `message_request` и не входит даже
в прежний `http_elapsed_ms`; подготовка текста/reply markup также вне него.

22 октября 2026 эти таймеры проверены в рабочем Sidekiq после native-only
релиза `6557ce563849` (образы и Python-контейнеры не менялись). Один синтетический
callback в разрешённом личном разговоре: ingress → Telegram accepted **1125 мс**,
HTTP **216 мс**, checkout **14,808 мс**, raw request **199,807 мс**, до входа в
response callback **199,699 мс**, callback **0,005 мс**, tail **0,104 мс**.
Сокет переиспользован, TLS setup **0 мс**. Это не подтверждает 200 мс end-to-end
и не является измерением getUpdates или отображения на телефоне. Предыдущий
одиночный callback был 1141 мс; разницу 16 мс нельзя считать доказанным ускорением.

Критические последовательные границы этого callback (от входа в ingress):

| Граница | Время от начала, мс |
| --- | ---: |
| Agent Bot webhook поставлен в очередь | 226 |
| Начало Python backend | 303 |
| Ответ поставлен в SendReplyJob | 757 |
| Начало SendReplyJob | 861 |
| Telegram подтвердил сообщение | 1125 |

Полная входящая native job длилась 447 мс и перекрывалась с backend; их нельзя
складывать. Backend: 489 мс, в том числе два Chatwoot API вызова — 469 мс,
сценарий — 2,8 мс. Вложенный atomic turn: 295 мс / 39 uncached SQL / 97 мс SQL.
Сопоставленный GET snapshot в Rails завершился за 85 мс (ActiveRecord 18,7 мс);
это серверный интервал, не всё время клиентского API-вызова. Ожидание
SendReplyJob — 104 мс. Доставка и безопасные getMe-проверки выполнялись
только через существующий прокси; прямой маршрут к Telegram не использовался.

Разбор high-очереди локализовал эти 104 мс: перед `SendReplyJob` выполнялся
`AgentBots::WebhookJob` длительностью 101,98 мс. Структурная проверка аргументов
нашла ровно `waiting_since` и `updated_at`, без других изменённых полей.
Такое событие нельзя просто удалить: consumer также повторяет незавершённую
синхронизацию ownership/routing. Подготовленный opt-in переносит тот же native
job в существующую `medium`-очередь, сохраняя payload, signing secret, delivery ID
и retry. Изменения назначения, статуса, неизвестные/смешанные delta и внешние
получатели сохраняют прежнюю очередь. На изолированной 4.19.0 проверены 14
комбинаций, сериализованный queue name и сохранение `medium` при `retry_job`;
ни одно задание не исполнялось. Это ещё не измерение выигрыша в production.

### Кандидаты оптимизации: проверены отдельно от production

На копии БД компактная сериализация **только публичного Telegram callback для
одного разрешённого внутреннего Agent Bot** сократила `AgentBotListener.message_created`:
10 чередующихся пар, query cache выключен, p50 **60,493 → 11,279 мс**, p95
**77,058 → 13,274 мс**, SQL **17 → 3**. Повторная совместная проверка с кодом
переноса waiting-only jobs дала p50 **52,821 → 9,343 мс**, p95 **72,628 → 12,231 мс**.
Это стоимость только listener после native UI priming, не всего ingress,
сохранения сообщения, HTTP, очередей или Telegram. Реальный Python consumer
получил эквивалентное событие; UI/jobs и mixed-recipient payload сохранились,
fixtures откатились, существующие строки не изменились, HTTP/jobs не исполнялись.
Для единственного внутреннего получателя намеренно не вызываются serializers
отброшенных полей; не следует обещать сохранение их исключений.

Ещё один кандидат — поздний snapshot состояния внутри подписанного webhook.
Одна свежая строка Conversation даёт и поля сценария, и `updated_at`-версию;
Message отдельно связывает input/contact/inbox/account. Python может пропустить
первый GET, но всё равно отправляет прежний authoritative atomic POST с lock,
ownership/staff/epoch/dedupe/CAS. Конфликт версии приводит к свежему GET и
перепланированию; неизвестный результат POST не разрешает слепую повторную
отправку. Snapshot никогда сам по себе не даёт silent ACK.

HMAC покрывает финальное тело. Oversize/невалидная подсказка оставляет обычный
webhook без snapshot. В Redis она хранится **отдельным Stream field**, а payload
остаётся старой пятикомпонентной схемой: старый consumer игнорирует подсказку и
делает GET. Совместимость старого reader и pending/restart/ACK проверяется на
локальном изолированном Redis; миграция, очистка или переименование streams не нужны.
Оценка верхней границы экономии GET в предыдущем личном sample — около 174 мс,
до вычета двух новых SQL/сериализации/конфликтов. Это гипотеза, не измеренный gain.
На изолированной копии с настоящими Rails/PG helper выполнил ровно два SELECT
(Message и Conversation), без flag — ноль. Один контрольный вызов занял
16,858 мс; это не percentile и не измерение общей экономии. Согласованность
версии/полей и oversize fallback проверены, синтетические строки откатились,
сетевые отправки и задания не запускались. Общий локальный регрессионный прогон
совместных изменений: 340 passed; native/Compose-набор: 40 passed, 10 skipped
(Docker Compose на Mac недоступен, его конфигурацию ещё нужно проверить на VM).

Все три новых переключателя в Timeweb Compose по умолчанию выключены:
`NEVIDIMY_AGENT_MESSAGE_PROJECTION`, `NEVIDIMY_AGENT_BACKGROUND_WAITING`,
`NEVIDIMY_AGENT_BUTTON_SNAPSHOT`. Публикация исходников/тестов не включает их
в production. Перед включением нужны совместная native-проверка, обновлённый
Python reader, проверка активных mounts/flags и контрольный личный callback.
После изменения conversation projection нужно обновить её проверенный source
pin в message projection; неизвестная комбинация обязана остаться native.

Последний подтверждённый live timing release остаётся `6557ce563849`.
Цель 200 мс end-to-end не достигнута; отдельные clone p50 нельзя складывать
с production-таймингами или выдавать за новый production percentile.

При этом rollout штатно остановил и запустил прежний ingress-контейнер, из-за
чего Docker сбросил исторический RestartCount 9 → 0. Старая финальная проверка
ошибочно ожидала прежний счётчик; исходный deployment unit остался failed.
Отдельная сверка подтвердила новый source/mounts, прежние images/env/credentials,
8 работающих сервисов, 5 active units, неприостановленный Sidekiq и внутренний/
публичный HTTPS. Результат записан как reconciliation; новый деплой и откат БД/
Redis не выполнялись. Для намеренно stop/start-контейнеров следует проверять
точный ID и нулевой новый счётчик, а не равенство старому историческому числу.

Отдельный эксперимент 22 октября: замена native `unread_incoming_messages.last(10)`
при формировании счётчика на capped SQL COUNT. На изолированной копии 4.19.0
прошли 270 чередующихся пар, полные payload совпали, jobs не исполнялись,
синтетические строки откатились. Заметного выигрыша нет: при 0 непрочитанных
медиана 8,09 → 8,74 мс, при 1 — 7,54 → 7,95 мс, при 10 — 9,40 → 9,33 мс.
Количество запросов осталось прежним (3). Кандидат не внедрён: снижение числа
создаваемых Ruby-объектов само по себе не оправдывает дополнительный runtime patch.

Целевые 200 мс необходимо подтверждать живыми измерениями этой границы, отдельно
для холодного/повторно используемого соединения и разных действий кнопок.
Локальный тест буфера, низкая задержка ack и время записи Message этого не доказывают.

В закреплённом native presenter `webhook_data` сначала строит обычное дерево
`messages`, а затем безусловно заменяет его webhook-представлением. Опциональный
`webhook_presenter_fast_path.rb` исключает только этот выбрасываемый расчёт.
Он включается лишь для проверенных исходников и цепочки native/EE методов;
неизвестная версия отключает оптимизацию. Итоговые поля webhook, SLA и jobs не
меняются. `tests/timeweb_webhook_presenter_live_probe.rb` сравнивает полные payload
и read-only SQL/allocation counters только на изолированном API-разговоре.

`conversation_broadcast_fast_path.rb` устраняет ещё одно выбрасываемое дерево:
для `CONVERSATION_UPDATED` штатный ActionCable job всё равно заново читает
разговор и формирует полный payload при выполнении. Listener передаёт только
display ID, а native `broadcast` добавляет account ID; выбор получателей и
проверки доступа остаются штатными. Другие события не меняются. Оптимизация
включается только при совпадении исходников listener/broadcast/job и наличия
штатного refresh для этого события. При неизвестном контракте остаётся native
путь. Initializer загружается до `turn_timing`, сохраняя внешний timing wrapper.
Live probe сравнивает конечные payload и получателей, отдельно замеряя listener
и worker в read-only транзакции, с test job adapter и заглушкой ActionCable.
На изолированной копии 4.19.0 все конечные payload и получатели совпали в 10
чередующихся парах. Медиана listener: 58,62 → 18,29 мс; uncached SQL-запросов:
15 → 5, выделений объектов: 5902 → 1339. Фоновый worker по-прежнему формирует
полные данные. Это измерение одного компонента, не всей Telegram-доставки.

Уведомление о доставке со статусом `sent` игнорируется до помещения в очередь:
у него нет действий в service. `failed`, `delivered` и `read` продолжают обрабатываться.

`agent_bot_self_event_filter.rb` дополнительно исключает до сериализации только
помеченный `message_created` от AgentBot самому себе в точный согласованный
внутренний HTTPS-webhook: текущий Python consumer возвращает для него no-op.
Native исходники/serializers закреплены, неизвестный вариант остаётся native.
Уведомления другим ботам, сообщения User/Contact, delivery/status events,
ActionCable и native SendReplyJob сохраняются.

`agent_bot_conversation_projection.rb` передаёт в наш точный внутренний
HTTPS-webhook компактное `conversation_updated`: display ID, имя события и
полный native `changed_attributes`. Python consumer использует только эти поля,
затем заново проверяет владельца разговора и синхронизирует планировщик.
Событие не удаляется; исходные job, подпись, secret, UUID и выбор получателей
сохраняются. Другим Agent Bot передаётся полный native payload. Если получатели
смешанные, полный payload строится до первого enqueue: ошибка сериализации не
должна приводить к частичной отправке.

Оптимизация включается флагом `NEVIDIMY_AGENT_CONVERSATION_PROJECTION=1`
только для закреплённых исходников 4.19.0 и известных цепочек методов;
неизвестный контракт сохраняет native поведение. Проверка исходников выполняется
при загрузке, а не на каждом событии. Clone probe с read-only транзакцией,
синтетическими получателями и test adapter подтвердил равенство потребляемых
полей, полного payload остальных получателей и контракта jobs. В 10 чередующихся
парах internal-only медиана listener снизилась с 41,72 до 0,57 мс, uncached SQL —
с 13 до 0, выделений объектов — с 5155 до 284. Для смешанных получателей полный
расчёт остаётся: медианы 40,43 и 42,17 мс. Это изолированное измерение компонента
с подготовленными привязками получателей, не всей production-цепочки и не
подтверждение цели 200 мс.

`interactive_jobs.rb` разделяет два существующих worker-потока Sidekiq 7.3.10:
один обслуживает штатную очередь `high` (webhook, доставка, activity message),
второй — остальные очереди в прежнем порядке. Concurrency прикладных очередей
остаётся 2. Штатный `sidekiq_alive` 2.5.0 добавляет при startup отдельную
healthcheck-капсулу с двумя потоками: итоговый `total_concurrency` равен 4,
а не 2. Эти healthcheck-потоки оптимизация не добавляет и не меняет.
Имена очередей, Redis jobs, retries и FIFO внутри каждой очереди не меняются.
Откат не требует миграции заданий. Неизвестная версия, weighted/custom capsules
или другое прикладное concurrency на этапе установки сохраняют прежнюю
конфигурацию. Лог рабочего процесса
`nevidimy_interactive_jobs` при startup подтверждает применённое разделение;
проверка конфигурации в отдельном runner не заменяет этот лог.

Тот же initializer не ставит только доказанно пустой `SendReplyJob` для входящих
и приватных Telegram Message: закреплённый native service всё равно завершился
бы без записи или отправки. Строки сообщений, остальные callbacks и UI events
сохраняются. Публичные ответы, attachment delay, другие каналы и неоднозначная
метаинформация остаются на native пути. Проверка source digest/owner отключает
эту оптимизацию при неизвестном коде; реальный контракт проверяется в pinned image
с тестовым job adapter, без выполнения заданий и отправки сообщений.

Для обновления с Chatwoot 4.18 на 4.19 guard допускает оба проверенных исходника
`SendReplyJob`. В 4.19 перед отправкой каналу добавлена обработка
`content_attributes['translation_pending']`: такое задание нельзя считать пустым,
даже для входящего или приватного сообщения. Любое truthy-значение Ruby сохраняет
native job; неизвестные исходники и некорректные attributes также сохраняют native
поведение. Это совместимость интеграции, не подтверждение выкладки новой версии.

Метки ограничены типом события, этапом, нормализованной операцией, HTTP-методом,
классом статуса и результатом. В них нет текста, URL, параметров, токенов, email,
ID разговора, сообщения или request ID. Неизвестные значения объединяются в
`other`. Коды без HTTP-ответа попадают в `status_class="error"`.
Метрики не вызывают LLM и не делают дополнительных сетевых запросов.

## Лимит памяти и диагностика Sidekiq

Для VM с 8 ГиБ RAM в Timeweb Compose закреплён `mem_limit: 2048m` для Sidekiq
(2 ГиБ), чтобы лимит сохранялся при пересоздании контейнера. Применение к рабочему
контейнеру проверяется отдельно: изменение конфигурации не подтверждает выкладку.

Не запускать полную Rails-диагностику, включая `rails runner`, через `docker exec`
в рабочем Sidekiq: дополнительный Rails-процесс делит его memory cgroup и может
вызвать OOM. Для такой диагностики использовать изолированный clone и отдельный
cgroup; на production проверять image ID, read-only mounts, SHA исходников и
здоровье без нового Rails boot. Успех clone-проверки не выдавать за introspection
wrapper в уже работающем процессе.

## Изолированное сравнение Ruby YJIT

`tests/timeweb_native_yjit_probe.rb` измеряет native `Messages::MessageBuilder`
на закреплённых Chatwoot 4.19.0 / Ruby 3.4.4. Это **не production runner**:
запуск допустим только в отдельном контейнере с существующей изолированной
копией БД, отдельным Redis и проверенным `verify-full`. Launcher должен до
инициализации Rails запретить Sidekiq enqueue и включить ActiveJob test adapter.
Не запускать через `docker exec` в рабочем Chatwoot/Sidekiq.

Для сравнения используются два последовательных процесса с одинаковыми
образом, read-only initializer mounts и ресурсами, меняется только YJIT.
Каждый процесс проверяет фактический `RubyVM::YJIT.enabled?`, выполняет 100
прогревочных и 30 измеряемых пар входящее/исходящее. Создаются только новые
помеченные контакты/разговоры в проверенном API-inbox клона. Native callbacks
сохраняются, задания перехватываются и никогда не исполняются. Неизвестные
listeners, external hooks и изменение ранее существовавших core-строк приводят
к отказу проверки; конфигурация клона ради прохождения guards не меняется.

Отчёт `YJIT_PROBE` содержит wall/CPU/GC, число и время SQL, RSS/peak RSS,
числовые YJIT stats и результаты инвариантов, без переписки и реквизитов.
Исходные записи остаются в клоне для проверки; скрытого удаления нет.
Benchmark исключает controller/auth, HTTP ingress, настоящую очередь, её
ожидание и Telegram. Его выигрыш нельзя выдавать за полный выигрыш кнопки.
После изменения production нужен отдельный замер ingress → Telegram acceptance.

Сравнение 22 октября 2026: одинаковый закреплённый образ и mounts, по одному
отдельному процессу с лимитом 1 GiB / 1 CPU, 100 warmup + 30 sampled pairs.
Оба прогона завершились с кодом 0, без OOM; старые core-строки не изменены,
ни одно захваченное задание не исполнялось, production не менялся.

| Медиана, мс | YJIT off | YJIT on |
| --- | ---: | ---: |
| Входящий MessageBuilder, wall | 139.850 | 145.518 |
| Входящий MessageBuilder, thread CPU | 80.688 | 74.243 |
| Входящий MessageBuilder, uncached SQL | 67.459 | 88.755 |

RSS после samples: 441516 → 472440 KiB. Число SQL на сообщение осталось

## Изолированный замер обязательного Telegram-прокси

`tests/timeweb_proxy_latency_probe.py` делает 10 последовательных read-only
`getMe` через **только** `http://telegram-proxy:3128`. Прямого fallback нет;
проверка сертификата/hostname включена, redirects выключены. Один aiohttp
connector переиспользует соединение; каждый ответ полностью прочитан и проверен
на ожидаемую идентичность бота. `getUpdates` и отправка сообщений отсутствуют.

Запускать только в отдельном контейнере с собственным лимитом памяти, не через
`docker exec` рабочего ingress. Launcher должен проверить API/SSH/маркер VM,
точные image/network и неизменность production, передать только две переменные
окружения (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_PROXY_URL`) закрытым способом.
`PROXY_PROBE` выводит только тайминги, булевы проверки и разрешённые классы ошибок;
`first_byte_ms` означает первый байт **тела** ответа, не raw HTTP/TLS byte.

Замер 22.10.2026, run `707a28a6e6ec`, отдельный read-only контейнер 512 МиБ
без swap, тот же ingress image/network: 10/10 успешны, завершение exit 0,
OOM отсутствует, production identities/секреты/исходники не изменились.
Первый запрос — 459.067 мс, в том числе setup соединения 345.168 мс.
Остальные 9 запросов с reuse: 69.551–222.319 мс, медиана 79.610 мс.
Это маленькая выборка `getMe`, **не** SLO, не время `sendMessage` и не полная
обработка кнопки. Она показывает, что ранее измеренные 316 мс `sendMessage`
нельзя объявлять постоянной минимальной задержкой прокси.

Отдельный native Ruby/Net::HTTP probe `tests/timeweb_proxy_latency_probe.rb`
(run `bc4ae6c72636`) проверил 20 `getMe` в одном TLS-сеансе через тот же proxy.
Setup — 240.700 мс; медиана запросов с пустым телом — 63.011 мс, с `{}` —
62.801 мс. Тела чередовались, все ответы подтвердили идентичность бота.
Повторное соединение, redirects и retries запрещены; Rails не загружался.
Контейнер завершился с exit 0 без OOM, production остался неизменным.
Это не сравнение производительности библиотек и не замер `sendMessage`:
две маленькие последовательные выборки не контролируют сетевую нагрузку.
Результат лишь исключает утверждение о неизбежных 300 мс у Ruby/Net::HTTP
или небольшого JSON-тела; путь реальной отправки требует своего замера.

## Как подключить на Timeweb

У Timeweb есть [мониторинг ресурсов VM](https://timeweb.cloud/docs/cloud-servers/manage-servers/resource-stats)
и [проверки доступности](https://timeweb.cloud/docs/monitoring/types), но это не
гистограммы наших прикладных запросов. Для managed PostgreSQL Timeweb предоставляет
[Prometheus Exporter](https://timeweb.cloud/docs/dbaas/prometheus-exporter):
доступ зависит от сети BGP; для каждого узла репликации нужны собственные targets.
Фактическую доступность на кластере `4221087` нужно проверить перед подключением.
Пароли экспортера нельзя записывать в Git.

Для нашего Docker Compose-контура следующий шаг — закрытый Prometheus и Grafana.
Kubernetes ради мониторинга не нужен. До запуска проверь свободную RAM/диск,
задай лимиты ресурсов и хранения. Новые платные ресурсы, публичный доступ и новый
HTTPS-hostname требуют соответствующего согласования. Не открывай `/metrics`,
9090 и Grafana без контроля доступа.

Пример scrape-конфига для Prometheus **в той же Docker-сети**:

```yaml
scrape_configs:
  - job_name: nevidimy-agent
    scrape_interval: 15s
    scheme: https
    metrics_path: /metrics
    static_configs:
      - targets: [agent-bot:8080]
    tls_config:
      ca_file: /run/tls/ca.crt
      server_name: agent-bot
```

CA нужно смонтировать read-only из действующей конфигурации внутреннего TLS.
Не используй `insecure_skip_verify`. На произвольном внешнем сервере hostname
`agent-bot` не разрешается: пример не создаёт сетевой доступ автоматически.

## Запросы для Grafana

Медиана и p95 времени до создания ответа для кнопок (замени `0.95` на `0.5`):

```promql
histogram_quantile(0.95,
  sum by (le) (rate(nevidimy_first_reply_created_seconds_bucket{kind="callback"}[15m])))
```

Длительность исходящих запросов по операциям:

```promql
histogram_quantile(0.95,
  sum by (le, operation) (rate(nevidimy_chatwoot_api_request_duration_seconds_bucket[15m])))
```

Число запросов за интервал и доля серверных/транспортных ошибок:

```promql
sum by (operation, status_class) (increase(nevidimy_chatwoot_api_request_duration_seconds_count[15m]))

sum(rate(nevidimy_chatwoot_api_request_duration_seconds_count{status_class=~"5xx|error"}[15m]))
/
sum(rate(nevidimy_chatwoot_api_request_duration_seconds_count[15m]))
```

Среднее число API-запросов на нажатие:

```promql
sum(rate(nevidimy_event_api_requests_sum{kind="callback"}[15m]))
/
sum(rate(nevidimy_event_api_requests_count{kind="callback"}[15m]))
```

На графиках показывай и размер выборки. При отсутствии запросов доля ошибок и
квантили могут быть `NaN`; это не 0% ошибок и не нулевая задержка. Гистограммные
квантили — оценка внутри бакетов, а не точные квантили отдельных событий.
Для точного разбора одного события остаются content-free логи с request ID.
