# История сертификатов и неудовлетворённые запросы

## Что меняется

`women_help_pdf_certificates` содержит настоящие PDF (`record_kind=certificate`)
и восстановленные факты принятой Telegram отправки (`historical_issuance`,
`status=accepted`). Для настоящих документов по-прежнему обязательны код,
серийный номер, номинал, срок и все прежние PDF-реквизиты. У истории таких
реквизитов нет; неизвестный провайдер остаётся NULL. `accepted_at` — время
исходного сообщения, не доказательство прочтения или использования сертификата.

`women_help_certificate_requests` отдельно хранит конкретный выбор помощи,
идентичность контакта, исходный/последний диалог и сообщение, первое/последнее
обращение, причину и состояние. Причины `paused` и `out_of_stock` различаются.
Текущий обработчик пишет `paused`: глобальная пауза сама по себе не доказывает
отсутствие подходящего сертификата. Общий экран паузы и невалидные старые кнопки
не создают конкретный запрос.

Активный запрос один на контакт и пул. Повторы исходного события, включая
повтор после отмены запроса, не создают запись и не меняют время. Другой вид
помощи того же пула обновляет последнюю категорию, сохраняя первое место;
другой пул сохраняется отдельно. Список ключей событий хранится в этой же
строке. Получатели уже принятой отправки или исторической выдачи не попадают
в ожидание. Идентификация соответствует inventory: HMAC account/contact,
не Telegram user ID; операции используют общую блокировку получателя.

Заглушка, кнопки и запрет новых выдач не изменены. Точный read-only `resume`
существующих отправок сохранён. Новая история учитывается в `claim`, но
приоритет новых пользовательских ответов «уже получала → остатки» сейчас
не активирован. Автовыдачи после пополнения, закрытия ожидания при будущей
выдаче и автоматического восстановления старых ожидающих в этом изменении нет.

## Миграция и активация

Следовать `AGENTS.md` и `docs/deploy-timeweb-from-mac.md`: сначала свежие API,
SSH host key и marker целевой VM. Отсутствие проверенного SSH блокирует
изменения production; браузерная консоль не отменяет эту проверку.

1. Подготовить релиз и закреплённый Python image; сохранить предыдущие image IDs,
   Compose overlays, env, units и ссылку релиза. Не менять Telegram/LLM/TLS настройки.
2. Сделать и проверить root-only backup managed PostgreSQL. Текущие файлы аудита
   не заменяют резервную копию. Сохранить агрегаты inventory и исходящих сообщений.
3. Обновить **оба** потребителя inventory: backend Agent Bot и certificate-admin-bot.
   Старый admin image нельзя оставлять работающим с новой историей: его выборки
   не фильтруют тип строк. Не запускать второй Telegram poller и не обновлять
   Chatwoot/Redis/Caddy ради этой задачи.
4. `CertificateInventory.initialize()` выполняет миграцию и создание таблицы
   запросов в одной транзакции под advisory schema lock. Версия миграции хранится
   в технической таблице `women_help_certificate_schema_migrations`. При ошибке
   транзакция откатывается. На продакшене не запускать локальный PostgreSQL.
5. Проверить health, неизменность паузы и отсутствие новых исходящих сертификатов.
   При живой проверке не использовать личные/клиентские диалоги без согласования.

## Восстановление подтверждённых получателей

Скрипт не скачивает PDF, не читает их содержимое, не отправляет сообщения и
не создаёт схему. Он использует существующий закрытый аудит, выбирает только
явно ожидавших с принятой последующей PDF-отправкой и повторно сверяет в БД
inbox/bot/account, контакт, диалог, время, тип вложения, наличие внешнего receipt
и статус. В stdout — только агрегаты; исключения драйвера редактируются.

Из **обновлённого** контейнера с настроенным env, после миграции и проверки backup:

```sh
python -m scripts.backfill_certificate_history \
  /private-report/certificate-waitlist-audit-20261022-final-v2.json \
  --expected-recipients 17
```

Путь отчёта на VM:
`/opt/nevidimy/reports/certificate-waitlist-audit-20261022-final-v2.json`.
Он должен быть доступен внутри контейнера через root-only read-only bind mount;
не открывать доступ другим пользователям и не копировать его в образ/Git.

После успешного dry-run выполнить ту же команду с `--apply`. Все 17 записей
импортируются одной транзакцией. Повтор допускается только при полном совпадении
метаданных; конфликт с настоящей выдачей или другим источником откатывает весь
импорт. После commit скрипт читает все записи обратно и проверяет их содержимое.
Если до импорта эти же получатели успели создать ожидание, оно помечается
исполненным со ссылкой на историческую запись в той же транзакции, без отправки.
Ожидаемый первый результат: imported=17, duplicates=0, verified_recipients=17;
повтор: imported=0, duplicates=17. Если результат неясен, сначала dry-run и
чтение состояния, а не повтор с иными реквизитами.

Не включать сомнительные PDF, остальные контакты из аудита или прежних ожидающих
в этот импорт. Не очищать существующие получатели/сертификаты для обхода конфликта.
Проверить неизменность доступных PDF, S3 и исходящих сообщений отдельно.

Откат на прежний Python image после внесения истории небезопасен: старые выборки
не различают типы строк. Использовать совместимый исправленный релиз либо
отдельно согласованный план восстановления; не удалять историю автоматически.

## Локальные проверки

```sh
uv run pytest -q --tb=short tests/test_certificate_history.py \
  tests/test_certificate_requests.py tests/test_paused_certificate_request_tracking.py \
  tests/test_certificate_availability.py tests/test_certificate_history_backfill.py
```

`tests/test_certificate_tracking_postgres.py` по умолчанию пропускается. Для него
нужен отдельно созданный пустой PostgreSQL на Unix-сокете в task-specific
`/private/tmp/nevidimy-certificate-pg.*`, без TCP. Задать
`CERTIFICATE_TRACKING_TEST_SOCKET` и `CERTIFICATE_TRACKING_TEST_PORT`.
Каждый тест создаёт и удаляет только собственную случайную схему. Конфигурация
production не используется; данные исключительно синтетические.
