# Исторические ручные выдачи из таблицы

Этот импорт восстанавливает факты выдачи из согласованного снимка `Sheet1`
(`gid=0`) для account 1. Дата выдачи в таблице — основной источник: её точность
составляет календарный день. Время сообщения хранится отдельно как свидетельство
отправки и не подменяет дату выдачи. Наивное время исходного SQL-снимка трактуется
как UTC. Для этой партии все даты выдачи и сроки опросов находятся в прошлом.

Состав партии: 39 уникальных контактов и диалогов; для 38 принятие отправки
Telegram подтверждено технически, для одной строки факт выдачи засвидетельствован
таблицей. Эти основания различаются флагом `telegram_acceptance_verified`.
Подтверждение принятия не означает прочтение или использование сертификата.

Категория помощи нормализуется в один из четырёх ID: `food_card`, `children_card`,
`medicine_card`, `hostel_3_nights`. Провайдер — `ozon` или `pyaterochka`.
Для истории категория и провайдер проверяются независимо: историческая выдача
Ozon по детской помощи допускается, хотя текущая привязка пула может отличаться.
Произвольные типы из таблицы, имена клиенток и тексты переписки не переносятся
в нормализованные записи и manifest. Неизвестные код и срок действия не выводятся
из даты выдачи: поля `code`, `expires_at`, `expiry_date` отсутствуют.

## Закрытые локальные артефакты

Снимок, нормализованные строки, dry-run отчёт и manifest хранятся только в
игнорируемом каталоге `.runtime/`, с правами `0600` для файлов и ограниченным
доступом к каталогу. Не добавлять их в Git, образ контейнера или общедоступные
вложения. SHA-256 исходного снимка закрепляется в `source.snapshot_sha256`.
Идентификаторы в этих файлах также требуют закрытого хранения.

CLI — `python -m scripts.import_manual_certificate_sheet`. Исходный JSON содержит
`source: {spreadsheet_id, sheet_name: "Sheet1", gid: 0}` и `rows` с нормализованными
полями builder. SHA-256 вычисляется из точных байтов исходного файла. Файл обязан
быть обычным, принадлежать текущему пользователю, иметь права ровно `0600`
и не быть символической ссылкой. Временная метка сообщения с пробелом между
датой и временем нормализуется в ISO с `T`; отсутствие зоны означает UTC.

Подключение задаётся явно через `CERTIFICATE_DATABASE_URL` либо пять переменных
`CERTIFICATE_DATABASE_HOST`, `CERTIFICATE_DATABASE_PORT`,
`CERTIFICATE_DATABASE_NAME`, `CERTIFICATE_DATABASE_USER`,
`CERTIFICATE_DATABASE_PASSWORD`. Обязательны `CERTIFICATE_IDENTITY_KEY` и
`CERTIFICATE_DATABASE_SSL_ROOT_CERT`: PostgreSQL TLS проверяет CA и имя хоста
(`verify-full`). Общие настройки приложения и inventory initializer не загружаются.
TLS-контекст создаётся так же, как в asyncpg: `PROTOCOL_TLS_CLIENT`, явная загрузка
CA, обязательная проверка цепочки и имени хоста. Это сохраняет `verify-full`
и совместимость с CA провайдера: дополнительные строгие X.509-флаги Python 3.14
из `create_default_context` требуют отсутствующий у этой CA Authority Key Identifier.

```sh
uv run python -m scripts.import_manual_certificate_sheet \
  --source .runtime/manual-certificates/source.json \
  --output-dir .runtime/manual-certificates/dry-run \
  --mode dry-run --expected-count 39 --expected-inbox 5
```

Dry-run выполняет preflight в транзакции `READ ONLY`. Исходное сообщение обязано
быть исходящим, публичным и связанным с правильными account, Telegram inbox,
контактом и обоими ID диалога. PDF проверяется через attachment/ActiveStorage:
имя заканчивается на `.pdf`, MIME равен `application/pdf`. Содержимое PDF,
сообщений и имена клиенток не читаются. Флаг принятия Telegram должен совпадать
со свежим состоянием: статус не равен ошибке `3`, внешний `source_id` непуст.
Реальный receipt сохраняется только внутри evidence исторической записи;
manifest и stdout его не содержат.

Сначала выполнить dry-run: проверить 39 строк, уникальность контактов, display
и внутренних ID диалогов, исходных сообщений и ссылок на строки. Повторно сверить
account/contact/conversation/message и основания принятия отправки; вывести
только агрегаты. Остановка из-за несовпадения не разрешает пропускать строки
или менять ожидаемое число, чтобы получить успешный результат.

Перед любым production apply действуют проверки цели и резервной копии из
`AGENTS.md` и `docs/deploy-timeweb-from-mac.md`. Apply импортирует только
исторические факты одной транзакцией; ошибка или конфликт откатывает всю партию.
Повтор допустим только при совпадающих метаданных и стабильном `source_ref`
вида `sheet:<spreadsheet_id>:0:<row>`. После commit проверить записи чтением,
сопоставить агрегаты и сохранить закрытый отчёт. При неоднозначном результате
сначала перечитать состояние и повторить dry-run.

Apply дополнительно требует закрытый JSON-файл подтверждения уже проверенной
резервной копии: `verified: true`, `sha256` (64 hex), абсолютный `archive_path`
и положительный `toc_entries`. Сам CLI резервную копию не создаёт и не объявляет
её проверенной. Файл подтверждения также должен иметь права `0600`.

```sh
uv run python -m scripts.import_manual_certificate_sheet \
  --source .runtime/manual-certificates/source.json \
  --output-dir .runtime/manual-certificates/applied \
  --mode apply --expected-count 39 --expected-inbox 5 \
  --backup-attestation .runtime/manual-certificates/backup-attestation.json
```

Внутри одной apply-транзакции выполняются preflight, узкая миграция, импорт,
полное чтение записей обратно и сравнение защищённых агрегатов до/после.
Проверяются статусы настоящих PDF с разбиением `is_test`, отсутствие таблицы
запросов, digest опросов и назначений специалистам именно 39 исходных диалогов.
Любое расхождение до commit откатывает импорт. После commit выполняются новое
чтение 39 записей и проверка точного повтора `(imported=0, duplicates=39)`;
транзакция проверки повтора всегда откатывается.

Оба режима записывают `followup-manifest.json` и `reconciliation-report.json`
с правами `0600` в каталог `0700`. stdout содержит только итоговые счётчики,
ошибки — только тип исключения, без SQL-параметров или credentials.

Для этого импорта требуется целевая v2-схема исторических записей, позволяющая
раздельно хранить основание из таблицы и техническую проверку отправки. Её
следует применять узкой миграцией под общей блокировкой схемы. Не вызывать
общий `CertificateInventory.initialize()` и не создавать/инициализировать
таблицу запросов ради этой операции. Сам builder manifest схему не читает
и не меняет. Совместимость v2 отдельно проверяет исполняющий импорт код.

После импорта число доступных PDF должно остаться прежним. Исторические строки
могут увеличить общий счётчик старого складского представления и при этом не
появиться в списке настоящих PDF; это не пополнение доступного запаса. Сравнить
число `available` отдельно от общего `total`. Импорт не отправляет сертификаты,
не изменяет S3, текущую паузу или пользовательский интерфейс.

## Manifest опросов

`app.chatwoot.manual_certificate_manifest.build_followup_manifest` — чистая
функция: принимает нормализованные строки, метаданные источника и явное
timezone-aware `generated_at`; возвращает JSON-совместимый словарь. Число строк
по умолчанию строго равно 39; параметр `expected_count` предназначен для
явных вызывающих сценариев и синтетических проверок. Результат сортируется
по строке таблицы, независимо от порядка входных записей.

Верхний уровень фиксирует `apply: false`, `schema_version: 1`, `account_id: 1`,
время формирования, метаданные снимка и обязательные capabilities:

- `historical_certificate_survey_copy`;
- `recheck_existing_certificate_followups`.

В каждой записи есть стабильный `job_key` вида `certificate:manual:1:<contact_id>`,
контакт и оба ID диалога, исходные сообщение и дата, провайдер/категория,
`currently_human_assigned`, `source_ref` и ссылка Google Sheets на конкретную
строку. `payload` описывает `screen: s5`, `state: pending` и контекст
`{aid_id, historical_survey: true}`. `due_at` — ровно 10:00 Europe/Moscow через
четыре календарных дня после даты выдачи. Истёкший срок не переносится на время
формирования. Для согласованной исторической партии будущий `due_at` запрещён.

`pending` внутри файла — предложение будущего состояния. Файл не пишет
`scenario_followups`, не активирует задания и не вызывает Chatwoot API.
`currently_human_assigned` отражает снимок, а не разрешение отправки: будущий
исполнитель обязан заново проверить актуальное назначение специалисту,
существующие certificate-followups, ответы и отмены. Уже отправленные,
отвеченные или отменённые задания не должны создавать повторный опрос.

## Почему активация пока заблокирована

Текущая ветка ответа «Пока нет» обещает, что сертификат ещё действует. Для старых
ручных выдач его срок неизвестен, поэтому это обещание непригодно. До отдельного
изменения на нейтральный исторический текст capability
`historical_certificate_survey_copy` не выполнена. До повторной проверки уже
существующих опросов также не выполнена
`recheck_existing_certificate_followups`.

Создание manifest и импорт истории не разрешают активацию. Текущий интерфейс
и тексты в этой задаче не меняются; отправка, изменение Chatwoot attributes и
другие действия активации должны оставаться заблокированными до выполнения
обоих условий и отдельного запуска согласованного механизма.

```sh
uv run pytest -q --tb=short tests/test_manual_certificate_manifest.py \
  tests/test_manual_certificate_sheet_import.py
```

Тесты используют только синтетические идентификаторы, даты и метаданные.
Им не требуются credentials, клиентские данные, база или сеть.
