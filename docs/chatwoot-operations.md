# Telegram и Chatwoot: эксплуатация

Актуальный production — Timeweb: см. раздел «Timeweb: новый контур» ниже.
Инструкции Yandex/Podman и `just deploy-prod` ниже сохранены как исторические;
к текущей VM их применять нельзя.

Telegram подключён штатным каналом Chatwoot. Новая переписка хранится в БД
Chatwoot; Python получает подписанные события и сохраняет ответы через API.
Прежний `women-help-bot` после переключения должен быть остановлен и отключён
от автозапуска. Его БД не удаляется; старые сообщения автоматически не импортируются.

## Где искать сообщения

В кабинете откройте Conversations → All. Разговоры бота обычно имеют статус
`Pending`; стандартный фильтр `Open` их скрывает. Выберите все статусы.
Сам статус не определяет владельца: смотрите назначенного сотрудника или
`/system_info`. Рабочий канал называется «Telegram — Невидимый фонд».

Канал «Техническая проверка интеграции» нужен только для серверных проверок.
Он использует тот же Agent Bot, но не отправляет сообщения пользователям Telegram.

## Очереди, подключение специалистки и возврат боту

- Вся переписка видна всем сотрудницам ещё до эскалации. Команды и папки —
  навигация, не ограничение доступа. Начальные очереди: «Дежурные» и «Юристы».
  Запрос человека назначает подходящую команду и добавляет приватную заметку:
  участникам команды с доступом к inbox приходит уведомление в колокольчике.
  Поле «Запрошен дежурный» (`handoff_requested`) отмечает запрос.
  Само уведомление не отключает бота и не назначает конкретного человека.
  Сотрудниц нужно добавить в нужную команду и дать доступ ко всем рабочим inbox.
  Chatwoot объединяет уведомления одного разговора: последующие сообщения
  обновляют уведомление в колокольчике, а заметка об эскалации остаётся в истории.
- Чтобы подключиться самостоятельно, откройте разговор (`Open`) и назначьте
  его себе. После этого можно отвечать в штатном поле Chatwoot.
- Для передачи используйте поле «Команда» справа либо макрос «Передать юристам» /
  «Передать дежурным». Вся новая команда получает уведомление. Повторная доставка
  одного события не создаёт дубль заметки. Ручной выбор приоритетнее решения модели.
- Режим `human` действует, пока в Chatwoot назначен сотрудник. Публичный ответ без
  назначения закрепляет разговор за отправителем; существующее назначение не меняется.
  Перевод команды не меняет владельца. Снятие назначения возвращает бота, в том числе
  после рестарта или пропущенного webhook. Для макроса **«Вернуть боту»** откройте
  «Личная заметка», в пустом поле введите `#` и выберите «Вернуть боту» в меню
  макросов. Это не отдельная кнопка рядом со статусом разговора; сам символ `#`
  отправлять не нужно.
  Он оставляет приватную
  управляющую заметку; Python снимает назначение, переводит статус в `Pending`
  и сохраняет подтверждение. Переписка, заявки, очередь и контекст не удаляются.
  Закрытие освобождает специалиста: на новый входящий отвечает бот. Закрытие без
  макроса «Консультация завершена» не отмечает заявку как выполненную.
  Кнопки клиента не отбирают активный разговор у специалиста.
  Поле «Кто отвечает» — вычисляемое; не редактируйте его вручную.
- `/clear` работает и после эскалации, и при подключённом человеке: сбрасывает
  только контекст/сценарий бота, сохраняя переписку, заявки, запрос дежурному и
  назначение сотрудницы. Это техническое подтверждение, не возобновление AI при человеке.
  Кнопка назад
  восстанавливает предыдущее состояние; заявки не отменяются.
- `/start` при специалисте объясняет текущий режим, не сбрасывая форму.
  `/system_info` показывает сборку, канал, владельца и статус, не закрывая опросы.
  Новое входящее пробуждает отложенный разговор; фоновые опросы этого не делают.

### Добавление нового направления без деплоя

Создайте команду в Settings → Teams, опишите её специализацию и добавьте участниц.
Бот перечитывает каталог и состав команд при эскалации; отдельного справочника
специалистов в Python нет. Qwen выбирает ID из актуального каталога по описаниям,
получая обезличенную историю текущего контекста. Дополнительный вызов маршрутизации
делается только при эскалации, а не на каждой реплике; два основных вызова остаются параллельными.
Пустые команды исключаются из автоматического выбора. При неоднозначности, ошибке
маршрутизации или сигнале безопасности используется настроенная дежурная команда.
Не удаляйте её: `CHATWOOT_DUTY_TEAM_ID` — стабильный ID очереди по умолчанию.

Переименование не меняет маршрут: назначения привязаны к ID, не названию.
Новая команда не означает автоматического добавления новой услуги в каталог фонда.
Сохранённые папки персональные: новые сотрудницы могут пользоваться штатным списком
Teams либо сохранить фильтр по Team. Не ограничивайте папку только `Open`:
уведомлённая очередь может ещё находиться в `Pending`, пока продолжает бот.
Команды создаются без автоназначения: сначала все получают уведомление, затем
одна сотрудница назначает разговор на себя.

Деплой автоматически запускает `activate.py queues`; отдельно команда доступна как
`sudo python3 /opt/women-help-chatwoot/deploy/chatwoot/activate.py queues`.
Она создаёт две очереди, четыре общих макроса и папки для существующих сотрудниц;
при повторном запуске не дублирует их и не перезаписывает отредактированные макросы.
Для первоначального тестирования состав «Юристов» копируется из «Дежурных».
Заменить состав можно в Chatwoot без деплоя. Отсутствие или ошибка общей очереди
считается ошибкой настройки, а не успешной эскалацией.

## Сеть и запуск

Telegram ingress показывает короткое уведомление «Обрабатываю выбор…» при
нажатии inline-кнопки, до передачи события в Chatwoot. Оно не вызывает LLM,
не создаёт сообщения в истории и не означает, что событие уже сохранено.
Курсор Telegram сдвигается только после приёма события Chatwoot. Ошибка или
истечение срока уведомления не блокирует доставку; исходная клавиатура
сохраняется, чтобы при сбое можно было повторить выбор.

Штатный HTTP-клиент Chatwoot использует внутренний HTTP CONNECT прокси,
который библиотека `pproxy` подключает к `TELEGRAM_PROXY_URL`. Порт прокси
не опубликован на VM; разрешено только назначение `api.telegram.org`.
Telegram TLS не расшифровывается. Настройка хранится в root-only agent env.

Сервисы: `women-help-chatwoot` (PostgreSQL, Redis, Rails, Sidekiq, Caddy,
прокси) и `women-help-chatwoot-agent` (Python). Все контейнеры перезапускаются.
Образ Python включает файлы навыков, модель Presidio и метаданные релиза.

## Если оператор намеренно заменил адрес

Из локального проекта запустите `just chatwoot-refresh-address`. Команда получает
актуальный IP по постоянному ID VM из Yandex Cloud, обновляет тестовые домены,
перезапускает сервисы при изменении настроек и проверяет HTTPS. Затем она
обновляет сохранённый адрес Agent Bot в Chatwoot и Telegram webhook, не удаляя
переписку, каналы и накопленные Telegram updates. Повторный запуск проверяет
оба webhook даже тогда, когда адреса в env уже обновлены.

Команда восстановления не резервирует адрес и не устанавливает
периодическое отслеживание. Старые ссылки с IP в имени после намеренной замены не работают;
используйте новый адрес, напечатанный командой. Успешная проверка настройки webhook
не заменяет проверку доставки реального входящего сообщения из Telegram.

## Первичное подключение на VM

После установки Chatwoot и создания первого администратора, от root:

```sh
python3 /opt/women-help-chatwoot/deploy/chatwoot/activate.py backup
python3 /opt/women-help-chatwoot/deploy/chatwoot/activate.py prepare
python3 /opt/women-help-chatwoot/deploy/chatwoot/activate.py provision
```

Сначала соберите образ и проверьте прокси/обработчик. Перед `connect`
обязательно остановите старый polling — два обработчика нельзя включать вместе.

```sh
systemctl stop women-help-bot
python3 /opt/women-help-chatwoot/deploy/chatwoot/activate.py connect
systemctl disable women-help-bot
python3 /opt/women-help-chatwoot/deploy/chatwoot/activate.py status
```

`provision` сохраняет служебные токены и ключ подписи только на VM.
`connect` устанавливает нативный Telegram webhook; повторный запуск не создаёт
дубликаты. Проверьте HTTPS health, отсутствие новых ошибок webhook, появление
входящего сообщения и единственного ответа, затем передачу дежурному.

Для отката после подключения сначала остановите Agent Bot и удалите Telegram
webhook через Bot API, сохраняя pending updates. Только затем запускайте старый
polling. Не восстанавливайте старую БД поверх новых обращений. Резервные копии
сохраняются в `/opt/women-help-backups/chatwoot-connect.*` с закрытыми правами.

## Подготовка нового контура Beget с managed PostgreSQL

Перенос в Beget остановлен пользователем. Ниже сохранена подготовка; актуальный
новый контур — Timeweb, описанный в следующем разделе.

Этот вариант пока не развёрнут. Существующие команды `just deploy-prod`,
`activate.py` и systemd units привязаны к прежнему Yandex/Podman-контуру:
не запускайте их на новой VM без адаптации и проверки целевого сервера.

Для нового контура используется базовый `deploy/chatwoot/compose.yml` вместе с
`deploy/chatwoot/compose.managed.yml`. Дополнение требует **Docker Compose 2.24.4+**;
оно удаляет сервис локального PostgreSQL и его зависимости, а не создаёт вторую БД.
Исходный файл и прежнее локальное развёртывание не меняются.

В закрытом `/etc/women-help-chatwoot.env` задаются `POSTGRES_HOST`, `POSTGRES_PORT`,
`POSTGRES_DATABASE`, `POSTGRES_USERNAME` и существующий пароль `POSTGRES_PASSWORD`.
Python получает те же реквизиты базы через `CERTIFICATE_DATABASE_*`; пароль
`CERTIFICATE_DATABASE_PASSWORD` остаётся в отдельном `/etc/women-help-agent.env`.
Пароли не подставляются в YAML или аргументы команд. Каталог сертификатов остаётся
в той же managed БД, что и Chatwoot; отдельная база Python не создаётся.

Оба клиента требуют TLS с проверкой имени сервера (`verify-full`). До запуска
миграций нужно установить доверенный CA в контейнерах при необходимости и проверить
соединение из каждого клиента. Ошибку сертификата нельзя устранять отключением TLS
или его проверки. Redis и вложения Chatwoot по-прежнему используют постоянные тома.

Структуру можно проверить без запуска контейнеров и чтения файлов с секретами
(реквизиты ниже — только тестовые):

```sh
POSTGRES_HOST=database.example.test POSTGRES_DATABASE=default_db \
POSTGRES_USERNAME=cloud_user CHATWOOT_HOSTNAME=chatwoot.example.test \
docker compose --env-file /dev/null \
  -f deploy/chatwoot/compose.yml -f deploy/chatwoot/compose.managed.yml \
  --profile agent --profile certificate-admin --profile polling \
  config --no-env-resolution --quiet
```

`tests/test_chatwoot_managed_compose.py` проверяет настоящее объединение файлов
через официальный Docker Compose, без Docker daemon и сетевых запросов. При
отсутствии Docker Compose тесты пропускаются; отдельный бинарник можно указать
через `DOCKER_COMPOSE_TEST_BINARY`. Это проверка конфигурации, не подтверждение
запуска Chatwoot, подключения к Beget или доставки сообщений Telegram.

## Timeweb: новый контур

Целевые ресурсы: VM `9351701` / `nevidimy-prod-app`, PostgreSQL `4221087` /
`nevidimy-prod-pg`, проект `3044129`, `msk-1`. Перед удалёнными изменениями заново
сверяются ID, имя, проект и текущий IP через API. Старые `just deploy-prod`,
YC resolver, `activate.py` и Podman units здесь не используются. Пользователь
принял текущий закреплённый SSH-ключ; маркер
`/etc/nevidimy-deployment-target=timeweb-nevidimy-prod-app-msk-1` фиксирует
назначение сервера, но не является независимым доказательством его идентичности.

На VM установлен Docker из подписанного репозитория Ubuntu: Docker `29.1.3`,
Compose `2.40.3`. Репозиторий Docker и Docker Hub с VM были недоступны; образы
официальных издателей доставлены через локальный `regctl`, с проверкой digest и
архитектуры `linux/amd64`. Chatwoot закреплён по manifest digest в закрытом
`/etc/women-help-chatwoot.env`. Повторный запуск не скачивает образы и не собирает
их неявно. Для обновления сначала доставляются и проверяются новые образы.

Используются три Compose-файла:

```sh
cd /opt/nevidimy/app
docker compose --env-file /etc/women-help-chatwoot.env \
  -f deploy/chatwoot/compose.yml -f deploy/chatwoot/compose.managed.yml \
  -f deploy/timeweb/compose.yml config --quiet
systemctl status nevidimy.service
```

`deploy/timeweb/bootstrap.sh` проверяет назначение хоста и устанавливает runtime,
не заменяя существующий. `deploy/timeweb/nevidimy.service` управляет ядром:
Chatwoot, Sidekiq, Redis и Caddy. Тома Redis, вложений и сертификатов постоянные;
Docker настроен на ротацию локальных логов. Python работает отдельно через
`deploy/timeweb/nevidimy-agent.service`, после ядра и проверки закрытого env-файла.
Telegram-профили по умолчанию выключены. Публичная самостоятельная регистрация
Chatwoot отключена.

Образ Python собран и проверен в изолированном контейнере без сети: русский
PII-редактор инициализируется, синтетический прогон потребовал около 370 MiB RSS.
Лимит backend-контейнера выбран 768 MiB с запасом на HTTP и рабочую нагрузку;
это не изменение тарифа VM. Постоянный backend запущен и healthy; штатный
перезапуск отдельного `nevidimy-agent.service` проверен на изолированном диалоге.

### База и сеть

Managed PostgreSQL — primary + две реплики, всего три узла. Лимиты инфраструктуры
остаются прежними: VM 4 760 ₽/мес, PG 6 320 ₽/мес, включая согласованные бэкапы и
IPv4. Расширения проверены именно в Timeweb PG18: `vector 0.8.6`,
`pg_stat_statements 1.12`, `pg_trgm 1.6`, `pgcrypto 1.4`, `plpgsql 1.0`.
Синтетические операции расширений и права владельца базы проверены.

После отдельного согласия пользователя БД получила публичный IPv4 для TLS.
Перед этим создана и привязана firewall-группа с политикой DROP: TCP 5432 только
от текущего IPv4 VM `/32`. Отрицательная проверка с локального компьютера показала
тайм-аут, разрешённые проверки из VM, Ruby и Python-контейнеров — TLS 1.3,
`verify-full` (для Python использован настоящий SQLAlchemy/asyncpg путь приложения).
Это не фильтрация приватной сети: firewall Timeweb её не ограничивает.

Используется домен БД из API/панели и официальный CA
`https://st.timeweb.com/cloud-static/ca.crt`. На VM он находится в
`/opt/nevidimy/certs/postgresql-ca.crt`, в контейнерах монтируется read-only как
`/run/certs/postgresql-ca.crt`. При смене публичного IP VM нужно сначала обновить
и проверить разрешающее правило; не открывать БД для всего интернета.

Физический автобэкап БД настроен ежедневно, хранится одна копия, начало
17.10.2026. На проверке 16.10 первая копия ещё не существовала; восстановление
не проверено. Сохранённое расписание не означает наличия успешного бэкапа.

### Проверенный запуск и оставшиеся условия

Штатный `rails db:chatwoot_prepare` выполнен дважды успешно. Создан первый
подтверждённый администратор аккаунта, не SuperAdmin; пароль сохранён локально в
`.runtime/timeweb-chatwoot-admin.json` с правами 0600, без отправки писем.
Секреты и токен управления Timeweb не включаются в архив исходников.

Внутренний healthcheck ядра успешен, в том числе после контролируемого
перезапуска контейнера Chatwoot. В отдельном синтетическом Channel::Api-разговоре
прошла настоящая цепочка Chatwoot → подписанный webhook → Python → DeepSeek →
ответ Chatwoot. Проверены завершённые классификации safety/support, ответ
специалиста, молчание бота при назначении человека, явный возврат боту и ответ
после перезапуска backend с сохранением состояния. Это не проверка доставки
Telegram или перезагрузки всей VM. На проверке 16.10 внешний HTTPS ещё не готов:
ACME возвращает connection timeout после TCP-соединения при проверке домена:
неуспешны HTTP-01 и отдельно TLS-ALPN-01. Причина сетевой недоступности для
валидатора не установлена; локальная внешняя проверка HTTP возвращает 308.
Провайдерский hostname VM не является публичным доменом: внешне не резолвится;
в Cloud пока нет управляемых доменов. Временная диагностическая конфигурация
не сохраняется, восстановлен стандартный автоматический выпуск Caddy.
Нельзя обходить эту ошибку отключением проверки сертификата или передавать
пароль через HTTP.

Пользователь выбрал DeepSeek V4.1 Flash через Timeweb AI Gateway
(`deepseek/deepseek-flash`). Добавлен отдельный Chat Completions transport;
прежний Yandex/Responses остаётся значением по умолчанию. Для Timeweb нужны
`LLM_PROVIDER=timeweb`, `TIMEWEB_AI_API_KEY`, `TIMEWEB_AI_MODEL`; модель не выбирается

Ориентир дальнейших расходов LLM — 10 000 ₽/мес, первоначальные изолированные
проверки разрешены без отдельного лимита. По отдельному согласию пользователя
создан бессрочный ключ AI Gateway `nevidimy-prod-llm`; независимый GET подтвердил
проект `3044129` и `expires_at=null`. Первоначально вместо секрета автоматизации

пользователь ввёл действительный секрет через интерактивный помощник
`.runtime/timeweb_llm.py --set-secret`; ID ключа и бессрочность перепроверены.
Ключ сохранён с правами 0600 локально и в `/etc/women-help-agent.env` на VM,
без вывода в чат. Токен управления Cloud на VM не передавался.
Синтетические Chat Completions проверки успешны локально, внутри Python-образа
и в живой изолированной интеграции Chatwoot. По отдельному согласию пользователя
в панели существующего ключа сохранён общий дневной лимит 300 ₽ и повторно
прочитано сохранённое значение. Принудительное исчерпание лимита не проверялось.

его через 24 часа, см. [документацию](https://timeweb.cloud/docs/ai-agents/pricing/token-limit).

Часовая автоматизация поддержки удалена по просьбе пользователя.

### Временный HTTP через SSH, без публичного входа

По просьбе пользователя 16.10 включён отдельный изолированный HTTP-режим.
К трём Timeweb Compose-файлам добавлен `deploy/timeweb/compose.http-local.yml`.
Он отключает `FORCE_SSL` только у Chatwoot/Sidekiq, задаёт
`FRONTEND_URL=http://127.0.0.1:18080` и заменяет публичные порты Caddy единственным
bind `127.0.0.1:18080:80`. Используется `deploy/timeweb/Caddyfile.http-local`
без автоматического HTTPS и без маршрута наружу к Python webhook.
TLS PostgreSQL `verify-full`, CA, firewall БД и HTTPS DeepSeek не ослаблялись.

HTTP-настройки сохраняются при старте сервиса через отдельный drop-in
`/etc/systemd/system/nevidimy.service.d/http-local.conf`; исходный unit и
HTTPS-конфигурация не изменены. Маркер целевого сервера проверяется по-прежнему.
Для возврата нужен отдельный согласованный переход: убрать только этот drop-in,
выполнить daemon-reload и применить исходные три Compose-файла после устранения
проблемы сертификата. Не удалять тома и не включать публичный HTTP.

На Mac открыт SSH local forward `127.0.0.1:18080` → VM `127.0.0.1:18080`
с закреплённым SSH-ключом. Сокет управления текущим туннелем:
`.runtime/timeweb-http-tunnel.sock`. Пока туннель работает, UI доступен по
`http://127.0.0.1:18080/app/login`; с другого компьютера этот localhost недоступен.
Пароли идут по HTTP только внутри localhost/Docker; участок Mac → VM зашифрован
SSH. Открытая вкладка браузера проверена, публичные 80/443/18080 недоступны.

После проверки единственного существующего подтверждённого администратора
штатно завершён Redis-флаг onboarding; второй аккаунт и SuperAdmin не создавались,
подписка на рассылку не отправлялась. При первоначальной проверке сохранялись
один аккаунт и один пользователь. Позднее добавлены синтетический тестовый разговор
и согласованный импорт истории, описанные ниже. Это временный доступ через SSH,
не публичный HTTP и не разрешение передавать по открытому интернету пароли
или клиентскую переписку.

Вход администратора через туннель проверен реальным `/auth/sign_in` (HTTP 200),
тестовая сессия сразу закрыта через `/auth/sign_out`. Пароль и токены не выводились.
Штатный Python entrypoint требует S3 для файлов; в локальном `.env` его реквизитов
нет. По отдельному согласию пользователя создан приватный бакет
`nevidimy-certificates` (Timeweb ID `583879`): Standard 1 ГБ за 1 ₽/мес,
без автоматического увеличения тарифа. Лимит исходящего трафика 1 ГБ/мес
сохранён и повторно проверен в панели. Timeweb проверяет его почасово,
поэтому это не жёсткий денежный потолок.

Панель скрывает S3-ключи от автоматического чтения. Пользователь вводит их
приватно в `.runtime/timeweb_s3_credentials.py`: оба запроса скрыты,
помощник проверяет настоящий `HeadBucket` по HTTPS и только при успехе
сохраняет `.runtime/timeweb-s3-credentials.json` с правами 0600. Доступы из
старой VM не извлекались, ключи не пересоздавались. Пользователь завершил ввод;
`HeadBucket` проверен также с VM. Настоящий S3-адаптер приложения загрузил и
прочитал синтетический PDF с совпадением SHA256; анонимный доступ отклонён.
Удалён только этот точный тестовый объект. Реальные файлы не использовались.

Локальный `.env` перенесён без изменения значений в закрытый файл
`/opt/nevidimy/secrets/source-local.env` на новой VM. Это резервный исходный
снимок, а не активная конфигурация: прежний `DATABASE_URL` и Yandex AI не
подменяют согласованные managed PostgreSQL и Timeweb DeepSeek.

Для Application API исправлено имя заголовка на `Api-Access-Token`: вариант
с подчёркиваниями проходил напрямую в Rails, но через Caddy возвращал 401.
На VM собран обновлённый Python-образ с проверкой совпадения исходников и
наличия исправления. Прикрепление Agent Bot исправлено на штатный параметр
`agent_bot` и теперь проверяет фактическую связь отдельным GET, а не только HTTP 200.

### Подписанный внутренний Agent Bot webhook

После отдельного согласия пользователя подключён read-only initializer
`deploy/timeweb/agent_webhook.rb` только в Chatwoot и Sidekiq. Он разрешает обход
SafeFetch исключительно для точного закрытого `NEVIDIMY_AGENT_WEBHOOK_URL` с
хостом `agent-bot`, портом 8080 и штатным secret-bearing путём Agent Bot. Нужны
тип события `agent_bot_webhook` и непустой существующий HMAC-секрет. Используется
штатная подпись Chatwoot; перенаправления и environment proxy запрещены,
тело ответа ограничено 64 KiB. Сам URL и секреты в документацию не выводятся.

Глобально `SAFE_FETCH_ALLOW_PRIVATE_NETWORK=false`: обычный SafeFetch-запрос
к внутреннему health endpoint по-прежнему отклоняется. В настоящем Python-
приёмнике валидная подписанная техническая проба вернула 204, отсутствующая,
изменённая и просроченная подписи — 401. После обновления Chatwoot нужно повторить
Ruby-регрессию и живой native-webhook E2E; не включать разрешение всех приватных сетей.

### Сохранённая история и Telegram

Источник — только `Downloads/nevidimy_full_20261008.sql.gz`. SQL не исполнялся;
локально разобраны COPY-данные, по проверенному SSH переданы только нужные записи.
Перед импортом создан закрытый custom-format `pg_dump` текущего Chatwoot в
`/opt/nevidimy/backups/before-history.*/chatwoot.dump`. Архив прочитан через
`pg_restore --list` и проверен по SHA256; полноценное восстановление не тестировалось.

Реальная синтетическая Rails/PG-проба прошла проверки отката, идемпотентности,
защиты от подмены/неполной выгрузки и отсутствия фоновых jobs. Сохранены и
повторно сверены 31 контакт и 785 сообщений: 293 входящих, 385 исходящих,
107 приватных заметок. Повторная сверка не создала новых записей. Старые кнопки
не перенесены, callbacks доставки не запускались. Источник остаётся Channel::Api
без внешней доставки и Agent Bot; 30 незавершённых разговоров Open реально
назначены существующему администратору и команде «дежурные», `reply_owner=human`.

Пользователь выбрал сначала испытать **`@nevidima_bot_mvp_bot`** и сам обновил
`TELEGRAM_BOT_TOKEN` в локальном `.env`. Новое значение проверено на VM через
HTTPS `getMe`: username совпал с выбранным MVP-ботом. Основной `@nevidima_bot`
не переключать автоматически; импортированную историю к тестовому боту
не присоединять. Предыдущий исходный снимок env остаётся закрытым и не перезаписан.

`deploy/timeweb/nevidimy-telegram.service` включён и запущен: он управляет
только `telegram-proxy` и `telegram-ingress`. Отдельный inbox MVP имеет Agent Bot;
импортированный источник к нему не присоединялся. Адаптер прокси не публикует порт и
получает отдельный минимальный env только с реквизитами прокси; ingress имеет
свой минимальный env без LLM/S3/администраторских ключей. Пользователь отдельно
подтвердил остановку старого обработчика именно MVP-бота и отправил `/start` с
уникальным тестовым параметром. Входящее принято нативным Chatwoot-каналом,
параметр найден в отдельном разговоре, ответ Agent Bot получил Telegram message
ID и статус Sent. Это подтверждение Bot API, не подтверждение прочтения человеком.
В том же nonce-подтверждённом личном разговоре Telegram принял служебный ответ
специалиста; Chatwoot передал управление человеку и затем вернул боту по приватной
команде. После отдельного перезапуска backend проверено сохранение владельца,
версии ownership, context epoch и workflow. Для подтверждения нового ответа
именно после этого перезапуска запрошен ещё один настоящий Telegram `/start`.
Синтетический incoming через Application API не повторялся после ошибки;
он не используется как доказательство доставки Telegram.
Наличие пустого webhook само по себе не использовалось как доказательство
отсутствия стороннего poller. Telegram updates не сбрасывались.

На старте обнаружены две проблемы: тяжёлый healthcheck повторно импортировал
Telegram SDK и завершался с 137; отдельно воспроизведены сетевые ошибки через
предоставленный SOCKS-прокси, в том числе без внутреннего HTTP-адаптера. Причина
сетевой нестабильности не установлена. Экспериментальная обёртка HTTParty удалена:
установленный штатный клиент поддерживает env-прокси и прошёл реальные запросы.
Проба `app.chatwoot.telegram_healthcheck` читает только Redis heartbeat без SDK,
а подготовка ingress повторяет временные сетевые ошибки с задержкой, сохраняя
тот же lock и SDK. Ошибки аутентификации не повторяются. Временные диагностические
контейнеры удалены; SSL-проверки и ограничения назначения не отключались.

Это тестовый MVP, не переключение клиенток в продакшен. Публичный HTTPS, длительная
стабильность прокси и восстановление из первого физического бэкапа ещё не проверены.
На финальной проверке VM, PG и все контейнеры запущены, ingress/agent/Chatwoot
healthy; у VM опубликован только loopback HTTP 18080, TLS БД включён. Сохранены
все незакоммиченные изменения и файлы импорта. Прошли 134 целевых локальных теста,
ruff и `git diff --check`; это не утверждение о прохождении всей тестовой базы.

## Внутренний TLS: подготовленный режим

Актуальный production — Timeweb, как описано выше и подтверждено пользователем
20.10.2026. Для него PostgreSQL уже использует `verify-full` с CA провайдера;
новый режим добавляет TLS к Redis, Chatwoot API и внутреннему Agent Bot webhook.
Активация новых соединений на сервере ещё не выполнена.

| Соединение после активации | Протокол и проверка |
| --- | --- |
| backend / Telegram ingress → Chatwoot | HTTPS / TCP 3000, CA и имя сервера |
| Chatwoot / Sidekiq → backend | HTTPS / TCP 8080, CA и имя; существующий HMAC сохраняется |
| Caddy → Chatwoot | HTTPS / TCP 3000, CA и имя сервера |
| Chatwoot / Sidekiq / backend / ingress → Redis | `rediss://` / TCP 6379, CA и имя; plaintext listener выключен |
| Chatwoot / Sidekiq / backend сертификатов → Managed PostgreSQL | существующий TLS / TCP 5432, `verify-full`, CA Timeweb |

Redis проверяет серверный сертификат; mTLS и новая парольная политика этим
режимом не включаются. Внутренние порты не публикуются. Локальный CONNECT на
3128 сохраняется: данные Telegram идут внутри сквозного HTTPS, внешний переход
прокси в записанном Timeweb-контуре защищён SSH. Этот управляющий локальный HTTP
не следует описывать как отдельное HTTPS-соединение.

### Штатный запуск Timeweb

`nevidimy.service`, `nevidimy-agent.service`, `nevidimy-telegram.service` и
`http-local.conf` используют общий `scripts/chatwoot_compose.py`. Он всегда
выбирает базовый Compose, managed-overlay и Timeweb-overlay. Если установлен
`/etc/systemd/system/nevidimy.service.d/http-local.conf`, все вызовы сохраняют
SSH-only UI: `127.0.0.1:18080`, без открытия публичных 80/443. В TLS-режиме Caddy
по-прежнему принимает локальный HTTP через SSH, а к Chatwoot подключается по
проверенному HTTPS. Сохранённые ограничения UI не снимаются.

Сертификаты генерируются на проверенной целевой VM, без вывода приватных ключей:

```bash
sudo python3 -m scripts.prepare_internal_tls --output-dir /opt/nevidimy/certs/internal-tls
```

В закрытом `/etc/women-help-chatwoot.env` сохраняются:

```dotenv
CHATWOOT_INTERNAL_TLS=1
INTERNAL_TLS_DIR=/opt/nevidimy/certs/internal-tls
POSTGRES_TLS_CA_FILE=/opt/nevidimy/certs/postgresql-ca.crt
```

Приватный CA приложения и существующий CA managed PostgreSQL не смешиваются.
`compose.tls-postgres.yml` на Timeweb не используется; локальный PostgreSQL не
запускается. Незакреплённые TLS-пути, неполный набор сертификатов, открытые права
ключа или подмена CA managed-БД останавливают общий запуск без возврата к HTTP.
Без новых TLS-настроек общий entrypoint сохраняет существующую конфигурацию.

До активации нужно перевести `NEVIDIMY_AGENT_WEBHOOK_URL` в закрытом env и
зарегистрированный `AgentBot.outgoing_url` в БД на HTTPS с тем же хостом,
портом и секретным путём. Подпись HMAC и глобальный
`SAFE_FETCH_ALLOW_PRIVATE_NETWORK=false` сохраняются. Значения URL и секретов
не выводятся. Entry point отклоняет TLS-режим, если env всё ещё содержит HTTP
webhook; совпадение с записью БД проверяется отдельно при live-приёмке.

Перед перезапуском нужны backup env/units/drop-ins, текущих image IDs, ссылка
на релиз и проверенный дамп managed-БД. Код и Python-образ с TLS поддержкой
доставляются и проверяются заранее. Сохраняются закреплённый образ Chatwoot,
`--pull never`, `--no-build`, тома и уже выбранный MVP Telegram-бот. Это изменение
транспорта не требует обновления Chatwoot или запуска старых Yandex-команд.

Проверка Compose без перезапуска (из `/opt/nevidimy/app`):

```bash
sudo python3 scripts/chatwoot_compose.py config --quiet
```

Для включения необходимо установить обновлённые Timeweb units и существующий
HTTP-local drop-in, выполнить `daemon-reload` и согласованный перезапуск всех
затронутых контейнеров. Не удалять volumes и не запускать параллельный poller.
При откате восстанавливаются прежние env, units/drop-ins и образы с теми же
томами; дамп БД автоматически не восстанавливается поверх новых сообщений.

### Сертификаты и приёмка

Leaf-сертификаты действуют 90 дней. Обновление сохраняет CA:

```bash
sudo python3 -m scripts.prepare_internal_tls --output-dir /opt/nevidimy/certs/internal-tls --renew
```

После выпуска контейнеры пересоздаются: процессы не подхватывают новые
сертификаты автоматически. Ключ CA не монтируется в контейнеры.

Локально проверены: HTTPS и отказ чужому CA/имени/plaintext; объединение Compose
для managed PostgreSQL и Timeweb с сохранением SSH-only UI; Redis TLS PING
и отказ plaintext; PostgreSQL TLS 1.3 и отказ plaintext; SQLAlchemy/asyncpg путь
приложения с `verify-full`; Caddy-конфигурация.

В изолированных контейнерах с пустой тестовой БД прошёл полный старт
Chatwoot 4.18.0 (`docker.io/chatwoot/chatwoot@sha256:a4b7eea7353a9b585d0f29f2c57c7549710db961b119f7f1561b2fe964f48f65`):
миграции, проверенный HTTPS Puma, отказ HTTP, Ruby healthcheck, TLS подключения
Rails и Sidekiq к PostgreSQL и Redis. Исправлено создание `tmp/pids` перед Puma.
Это не установление версии production и не проверка живой доставки Telegram.

Развёртывание этих изменений выполняется с локального Mac по
[инструкции деплоя](deploy-timeweb-from-mac.md). Облачная интеграция доступа
отменена пользователем и не является предварительным условием. Yandex CLI
не нужен. Серверный firewall и новые живые TLS-соединения ещё требуют приёмки.
`architecture-2.png` отражает сохранённую Timeweb-конфигурацию; после live-приёмки
новые внутренние подписи меняются на TLS с сохранением оформления.
