# Приёмка сценариев и устойчивости Chatwoot

## Что исправлено

- Новый HTML: 57 экранов, подтверждения заявок, темы юридических обращений,
  отзывы, возврат назад и сохранение бизнес-фактов после `/clear`.
- Владение разговором отражает видимое назначение сотрудника. Нет скрытого
  вечного `human` без сотрудника. Уведомление команды не выключает бота;
  публичный ответ сотрудника назначает его, снятие назначения и завершение возвращают бота.
- После завершения консультации сохраняется заявка и планируется опрос. Старые
  кнопки, повторы webhook и возврат назад не создают повторных заявок.
- Диагностика риска отделена от намерений. Запрос консультации не считается
  опасностью. Старые инструкции меню/анкет не конфликтуют с HTML runtime.
- Нативная JSON Schema Qwen ограничивает формат ответа; два вызова остаются
  параллельными. Не добавлялся regex-классификатор пользовательских сообщений.
- Webhook сохраняет событие в существующем Redis до HTTP 204; незавершённая
  обработка повторяется после рестарта. Healthcheck показывает деградацию.
- PDF в API inbox не ждёт несуществующего Telegram message ID. Публичный API
  действительно показывает вложение, но скрывает приватные заметки.
- Деплой устанавливает макрос «Консультация завершена». HTTP access log агента
  отключён, чтобы URL с секретом webhook не попадал в журнал.

Полный candidate: **163 отдельных тестовых разговора, 385 входящих клиентских
сообщений, 170 проверенных переходов по кнопкам**. Это не 163 свободных естественных
беседы: состав — 11 сквозных маршрутов, 1 цикл человек/бот, 63 классификации с
заданным контекстом, 77 вариантов экранов с заданной точкой входа, 4 таймерных
сценария, 6 контекстных/навигационных сценариев и 1 сценарий PDF.

Отчёт: `.runtime/chatwoot-tests/f7b4cde8ddf942daba401fc88056b6a7/report.json`.
Модель: `qwen3.6-35b-a3b`; temperature 0, reasoning none. Риск: **63/63**;
намерение: **62/63 (98,4%)**; оба ответа модели корректны по формату в **63/63**.
Оставшееся расхождение: нестабильность жилья классифицирована как конкретная
потребность, старый эталон ожидал свободный разговор. Правильная эскалация сработала.
Ярлык не скрыт и не исправлен в эталоне; во время кризисной ветки это диагностическое
расхождение, поскольку действие определяет safety policy. Для детской ветки дополнительно
проверено продолжение после эскалации в соответствующее меню.

Это результаты ограниченного набора, а не обещание 100% точности на будущих обращениях.
Предыдущие неуспешные прогоны сохранены рядом с финальным, не выброшены из истории.
Ручное объявление «всё хорошо» или только HTTP healthcheck за приёмку не принималось.

Покрытие Python-кода с учётом ветвлений: **69%** по всему `app`, HTML runtime **95%**,
Chatwoot service **91%**, очередь событий **96%**, сценарные эффекты **87%**.
В общий показатель входят старый standalone-контур и отдельная админка сертификатов.
Live-проверки PostgreSQL/S3/Chatwoot не включены в этот локальный coverage.
Пропущен только опциональный тест навигации старого PostgreSQL-хранилища.
Пять предупреждений относятся к deprecated SWIG-типам зависимости; тесты не падают.

## Изоляция и воспроизводимость

```sh
just chatwoot-acceptance candidate
just chatwoot-acceptance
# Все переходы уже развёрнутого сервиса, без расходования сертификатов:
uv run python -m scripts.run_chatwoot_acceptance --mode webhook --suites journeys ownership contextual screens
```

CLI сам определяет VM и проверяет metadata instance ID. Секреты остаются на VM.
Приватные отчёты (0600) лежат вне Git. Тестовые чаты явно обозначены техническими,
находятся в API inbox без Telegram и после проверки закрываются, не удаляются.
Тестовые PDF не имеют денежной стоимости; S3-объекты находятся в `test/`.
Рабочие сертификаты не выдавались и не сбрасывались. SQL-схема
`acceptance_adef9177aa1c4769a34dcffee4edf5c6` содержит только синтетические записи.

Реальная отправка сотрудника и клиентская видимость проверялись через API Chatwoot,
не визуальным нажатием в браузере. Таймеры проверялись с управляемыми часами сервиса:
многодневного ожидания в реальном времени не было. Telegram-транспорт не включён
в эту приёмку согласно согласованной границе. Права других пользователей, реальное
погашение сертификатов и организационный SLA «10 минут» этим прогоном не доказаны.

## Выкладка и ограничения

Целевая VM: `epdqi9moqfn8fqbe3g2n`, не другая машина.
Резервные копии БД, вложений и конфигурации: `/var/backups/women-help/20261003-acceptance/`.
Сохранены старые образы с тегом `before-acceptance-20261003` для отката.
Новый код рассчитан на один процесс Agent Bot. Очередь — at-least-once, не exactly-once.
Redis AOF everysec не гарантирует нулевую потерю при физическом отказе VM.
Неисправимое событие удерживает свою рабочую очередь и делает healthcheck красным;
остальные семь очередей продолжают работу. Для нескольких реплик нужен отдельный дизайн.

Статус выкладки и серверные результаты будут добавлены после проверки production.
