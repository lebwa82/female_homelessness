# Chatwoot DDS для аналитиков и ИИ

[Каталог](catalog.json) описывает семь фактов, измерения и мосты. Для каждой таблицы указаны источник, гранулярность, первичный ключ, логические связи, правила обновления и ограничения. Для каждого столбца указаны тип PostgreSQL, смысл NULL и преобразование. Раздел `requirements` связывает 105 исходных требований со столбцами DDS. [Словарь показателей](metrics.json) задаёт даты, фильтры и единицы подсчёта. [Примеры SQL](examples.sql) можно выполнять непосредственно в схеме `dds`.

## Гранулярность фактов

| Факт | Одна строка | Первичный ключ |
| --- | --- | --- |
| `fact_conversation` | Диалог Chatwoot | `conversation_key` |
| `fact_message` | Сообщение Chatwoot | `message_key` |
| `fact_consultation_request` | Запись запроса внутри диалога | `request_key` |
| `fact_followup` | Запись follow-up внутри диалога | `followup_key` |
| `fact_certificate` | Документ, связанный с областью загрузки по сообщению отправки, или историческая запись выдачи из отобранного диалога | `certificate_key` |
| `fact_certificate_request` | Запись очереди сертификатов | `certificate_request_key` |
| `fact_csat` | Ответ на опрос CSAT | `csat_key` |

UUID псевдонимизируют исходные идентификаторы в контексте аккаунта и сущности. Записи консультации и follow-up дополнительно привязаны к исходному диалогу. Одна карточка контакта соответствует одному ключу DDS. Слияния контактов по общим атрибутам нет. `account_id` задаёт область соединения. `aid_id` и `selected_aid_id` сохраняют разрешённый текстовый код вида помощи. Исходные идентификаторы отдельных объектов, содержание сообщений, вложения, реквизиты сертификатов и полные JSON объектов недоступны в DDS.

## Соединения и фильтры

- Для актуального среза применяйте `deleted_at IS NULL` к каждой таблице. Для необязательной связи используйте `LEFT JOIN` и отбор активной строки присоединяемой таблицы в `ON`.
- Соединяйте по описанной в каталоге паре ключей и равенству `account_id`. Логический внешний ключ может быть пустым или указывать за пределы области загрузки.
- Измерения по первичному ключу добавляют до одной строки на факт. Для двух фактов сначала агрегируйте каждый до общей гранулярности, например одного диалога, затем соедините агрегаты. Для фильтра по связи многие-ко-многим используйте `EXISTS` или список уникальных ключей.
- Полиморфный `fact_message.sender_key` соединяйте с `dim_contact` при `sender_type = 'Contact'` и с `dim_staff` при `sender_type = 'User'`. `dim_staff.account_type` часто отсутствует. `User` указывает на тип учётной записи отправителя. Ручное авторство требует отдельного подтверждения.
- У follow-up соединяйте `request_key` с консультационным запросом только при `target_kind = 'consultation'` и равных `conversation_key`. `unresolved_target_key` служит непрозрачной ссылкой для диагностики. Целевой факт для неё неизвестен.
- В сертификатах `contact_key` и `conversation_key` отражают прямые ссылки источника и часто равны NULL. Для установленной связи используйте `resolved_contact_key`, `resolved_conversation_key` и `link_origin`. Значение `direct` указывает на наличие хотя бы одной прямой ссылки. Недостающая связь может дополнительно восстанавливаться. При отсутствии прямых ссылок `send_message` указывает на восстановленный диалог отправки, а `unresolved` обозначает отсутствие разрешённой связи.
- В `dim_certificate_pool` и `bridge_pool_aid` попадают пулы, связанные с отобранными сертификатами или записями очереди. Связь с провайдером относится к тем же пулам. `bridge_pool_aid` описывает допустимые пары таких пулов и видов помощи. Для выбранного вида помощи используйте `fact_certificate.selected_aid_id`. `bridge_certificate_request_event` связывает одну запись очереди с уникальными ссылками на события. Очередь считайте по факту запроса.
- `dim_label`, `dim_tag` и их мосты могут быть пустыми. Сопоставление `bridge_label_tag` использует точное однозначное совпадение названий из согласованного списка внутри аккаунта. Неоднозначное совпадение попадает в контроль качества. Для меток диалога в `bridge_object_tag` используйте `taggable_type = 'Conversation'` и `context = 'labels'`. Каноническое назначение учитывает объект, тег и контекст. Несколько совпадающих исходных назначений образуют одну связь.

## Даты, NULL и история

- `timestamptz` хранит момент времени. Входные метки без зоны трактуются как UTC. Для отчётов по московскому дню используйте `(field AT TIME ZONE 'Europe/Moscow')::date`. `issued_on` имеет тип `date` и уже представляет дату из источника.
- NULL означает отсутствие корректного доступного значения. Отдельные недопустимые скаляры заменяются на NULL с отметкой контроля качества. Если запись сценария не проходит проверку структуры или допустимого состояния, запрос или follow-up может отсутствовать целиком. Оставляйте NULL отдельной группой, когда отсутствие важно для анализа. Для показателя по дате берите дату из словаря. Дата создания карточки контакта не датирует первое обращение за помощью.
- Срез содержит последние опубликованные строки. `loaded_at` показывает момент записи текущей версии в DDS. `deleted_at` показывает момент обнаружения удаления по полному чтению. У дочерних записей JSON исчезновение также фиксируется после полного перечитывания затронутого диалога. `row_hash` используется загрузчиком для сравнения значений.
- `dim_aid` формируется из кодов в фактах и мосте применимости пулов. Исчезновение кода проверяется только при одновременном полном чтении всех сущностей, из которых строится измерение.
- История начинается с первого наблюдения DDS и содержит только зарегистрированные загрузчиком изменения. Несколько изменений между загрузками могут дать одну наблюдаемую версию. Для полноты среза учитывайте последний успешный запуск и дату последней полной сверки.

## Интерпретация показателей

Подсчитывайте создание запроса консультации по `requested_at`, а отметки завершения по `completed_at`. Это разные события, которые могут попасть в разные дни. Первые и последние даты запроса в очереди задают интервал записи. Число повторных попыток остаётся неизвестным. Оценка CSAT от 1 до 5 относится к опросу CSAT. Состояние follow-up `answered` учитывается в показателях follow-up.

Для сертификатов показывайте статусы раздельно по `record_kind`. Историческая запись попадает в срез по аккаунту, диалогу и контакту. Документ инвентаря попадает в срез по сообщению отправки. Остаток сертификатов неизвестен. Неотправленные документы без связи с областью загрузки, включая доступные и зарезервированные, отсутствуют в срезе. Ноль означает отсутствие наблюдавшихся записей в выбранной группе.

`completed`, `resolved`, `delivered` и `answered` фиксируют состояния процесса. Для числа случаев оказанной помощи выводите «неизвестно». Для подтверждённого показателя понадобится источник с явным результатом помощи.

## Изменение схемы

Обновляйте контракт в [catalog.json](catalog.json) и генерируйте SQL из корня проекта.

```sh
uv run python -c 'from pathlib import Path; from analytics.dds.catalog import schema_sql; Path("analytics/dds/schema.sql").write_text(schema_sql(), encoding="utf-8")'
```

Проверка каталога сопоставляет ключи, связи, типы и ссылки mapping. Тест сверяет `schema.sql` с генератором, включая PostgreSQL COMMENT. DDL версии 1 создаёт таблицы DDS. Переход существующего DDS на новую версию потребует отдельной миграции.


## Полнота и неоднозначные ссылки

Рядом с графиками по дате показывайте полноту: число всех активных запросов, число с известным requested_at и число без даты. Для завершённых отдельно показывайте отсутствие completed_at. Для follow-up знаменатель полноты sent_at — активные sent/answered, включая строки с неизвестной датой. Два последних примера в examples.sql считают эти знаменатели без подстановки дня для NULL.

Очередь сертификатов агрегирует попытки, в том числе из разных inbox. Первые/последние ID и даты видны только для соответствующего разрешённого диалога. Если последний диалог вне scope, его aid/reason/status и ссылку исполненного сертификата скрываем. Массив source_event_keys не хранит принадлежность каждого промежуточного события inbox. Консервативный MVP публикует только однозначный единственный ключ при двух доступных концах очереди. Несколько разных ключей, смешанные области и повреждённые элементы дают код качества; отсутствие моста не означает отсутствие повторных попыток. Исчезновение связи из выбранного среза может означать отзыв видимости, а не удаление события в источнике.

Некорректный порядок requested/completed, first/last request и valid_from/expires_at сохраняется с отметкой качества. Длительности рассчитываются только после исключения соответствующей ошибки. Исходные неизвестные даты не восстанавливаются из статусов.

Для длительностей используйте обе известные даты и условие `completed_at >= requested_at` (аналогично first/last и valid_from/expires_at). Таблица ctl закрыта от аналитиков, поэтому сам SQL должен явно исключать отрицательные интервалы. Времена наблюдаемой истории не заменяют бизнес-даты.

Инструкция запуска и восстановления: [OPERATIONS.md](OPERATIONS.md).

Почасовой инкремент перепроверяет FK только обрабатываемых фактов. Изменение маленького измерения может оставить старую ссылку в неизменённом факте до суточной полной сверки. Используйте LEFT JOIN, равенство account_id и `target.deleted_at IS NULL` в ON; отсутствие измерения означает неизвестное.
