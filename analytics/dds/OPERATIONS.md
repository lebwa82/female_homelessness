# Локальная реализация и последующий запуск DDS

На этом этапе production не изменён. Команды записи требуют явного `--apply`; это защита от случайного запуска, а не разрешение менять рабочую БД.

## Проверка контракта

Из корня проекта: `uv run python -m analytics.dds validate`. Каталог содержит 19 таблиц и 105 требований. Для ИИ доступны catalog.json (поля/связи/семантика), metrics.json (определения показателей), README.md и examples.sql. Описания и PostgreSQL COMMENT генерируются из одного каталога и проверяются тестами.

## Конфигурация

Скопируйте config.example.json в закрытый каталог оператора. Заполните разрешённые inbox, исключённые тестовые контакты и согласованные названия меток; затем отдельно подтвердите scope (`scope_confirmed=true`). Пустой список меток означает отсутствие меток в срезе. Пустой список inbox блокирует запуск. Изменение scope, источника или HMAC-ключа существующего DDS требует контролируемой пересборки.

DSN задаются через DDS_SOURCE_DSN и DDS_TARGET_DSN в закрытом окружении. Не передавайте их аргументами команд или через историю терминала. Для удалённого PostgreSQL обязателен один канонический хост и sslmode=verify-full, CA задаётся sslrootcert либо PGSSLROOTCERT. Мультихост и query-переопределения адреса запрещены. Локальная тестовая БД допускает обычное подключение к loopback.

Файл identity_key_file должен содержать 32–4096 случайных байт, принадлежать пользователю worker и иметь права0600. Ключ не выводится и не включается в Git. Исходный и целевой пользователи различаются: source имеет только необходимый SELECT, target loader — права записи DDS/ctl и TEMP; миграции выполняются отдельно уполномоченным владельцем. Настройки бота и его реквизиты аналитический модуль не импортирует.

## Порядок команд

- `uv run python -m analytics.dds --config <закрытый-config.json> migrate --apply` — явно применить и проверить версию схемы на разрешённом target.
- `uv run python -m analytics.dds --config <закрытый-config.json> load --apply --full` — первоначальная загрузка/полная сверка.
- `uv run python -m analytics.dds --config <закрытый-config.json> load --apply` — инкремент с перекрытием48 часов; первый запуск автоматически полный.
- `uv run python -m analytics.dds --config <закрытый-config.json> status` — время последней публикации, режим и количество проблем.

Источник читается в REPEATABLE READ READ ONLY. Малые источники перечитываются полностью, сообщения и диалоги — по created_at/updated_at. JSON дочерних фактов перечитывается целиком для изменённого диалога. Раз в сутки нужен отдельный полный запуск. Worker ограничивает объём50 тыс. строк/16 MiB выбранных JSON, 16 KiB на JSON-проекцию записи; это MVP в памяти, а не гарантия максимального RSS. Превышение прерывает загрузку вместо публикации частичного среза.

Staging — временные таблицы с пакетной записью. Merge, отметки исчезновения, наблюдаемая история, DQ и checkpoint публикуются одной транзакцией. При сбое достаточно повторить запуск; при неуспехе checkpoint прежний. Сессионная advisory-блокировка предотвращает пересечение workers. Устаревший снимок отклоняется. Не очищайте существующий DDS и не сбрасывайте checkpoint для устранения ошибки.

## Качество и восстановление

DQ хранит только код, псевдоключ и run_id. Нет исходных payload, переписки и секретов. Некорректные скаляры дают NULL; новые некорректные дочерние записи карантинируются. Повреждение уже опубликованной структуры дочерней записи или известного списка событий блокирует новую публикацию. Для обрабатываемых строк пропавший FK становится NULL с кодом; неразрешимый обязательный мост карантинируется. Смена выбранных значений без смены source.updated_at сохраняет последнюю прочитанную версию с предупреждением. Даты не выдумываются.

Полный запуск отмечает исчезновение всех выбранных источников и JSON-детей удалённых/выведенных из scope диалогов. При инкременте такая отметка для JSON допускается только после полного перечитывания родителя. История содержит наблюдаемые состояния с момента запуска, не восстанавливает события между опросами. Для диагностики используйте ctl.etl_run, ctl.dq_issue и ctl.observed_state_history под операторской ролью; аналитикам ctl не выдаётся.

## Расписание, доступ и пилот

service/timer.example — не установленные units. Перед использованием подготовить отдельного системного пользователя, Python3.14 окружение и закрытые файлы, проверить пути, лимиты RAM/CPU и согласовать развёртывание. Ежечасный таймер запускает инкремент; отдельная пара reconcile.service/timer.example вызывает load --apply --full раз в сутки (время примера согласовать по нагрузке). Автодеплоя или рестарта бота в коде нет.

access.sql — разовый шаблон отдельной группы и login без пароля. Применять только после ревью прав и подтверждённой аутентификации. Он выдаёт SELECT на явные19 таблиц, проверяет наследование PUBLIC и исполняемые SECURITY DEFINER; не отзывает общие права приложения. SQL-команды не ограничивают маршрутизацию: аналитический клиент/proxy должен выбирать standby (например target_session_attrs=standby в его libpq-клиенте), проверять pg_is_in_recovery() после failover и не переходить на primary. TLS и приватный маршрут обязательны. Права на raw и ctl должны быть проверены отрицательными тестами.

Перед production заново проверить API/SSH-идентичность, snapshot схемы, резервную копию и актуальные метрики ресурсов. После включения наблюдать7–14 дней длительность/свежесть, размер DDS, CPU/RAM, WAL и lag. Начальные пороги: worker до5 минут, данные не старше двух периодов, резерв свободного диска6 GiB; устойчивые timeout, отставание или ухудшение p95 приложения требуют остановки/разбора. Для остановки отключить только таймер DDS и дождаться/остановить его worker; приложение и реплики не перезапускать. Ограничения памяти в service.example сначала подтвердить локальными/пилотными замерами.

Миграция версии1 additive/idempotent. Автоматического удаления схем, удаления пользовательских данных, повышения тарифа и неявного отката схемы нет. При несовместимой версии загрузчик останавливается. Откат кода допустим только с совместимым контрактом; сначала остановить расписание и проверить сохранённый каталог/версию.


## Связи между редкими обновлениями

При почасовом инкременте перепроверяются связи обрабатываемых строк. Если маленькое измерение изменилось, а старый диалог/сообщение не вошёл в окно, его прежний псевдоключ может сохраняться до обязательной суточной полной сверки. В запросах присоединяйте измерения через LEFT JOIN с `target.deleted_at IS NULL` в ON и равенством account_id; недоступный объект показывайте как неизвестный. Полная сверка исправляет такие ссылки и повторно разрешает появившиеся. Это ограничение MVP, поэтому ежедневную полную сверку нельзя пропускать.

ctl.etl_run содержит только успешно опубликованные запуски. Ошибки и отказ при занятой блокировке выводятся как обезличенный JSON результата команды и должны сохраняться в журнале worker. Не публикуйте полный traceback драйвера с реквизитами.
