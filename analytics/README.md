# Аналитика бота

Здесь сохраняются воспроизводимые запросы, расчёты и агрегированные отчёты. Переписки, контактные идентификаторы, ключи и файлы сертификатов в Git не добавляются. `private/` исключён из Git; даже псевдонимы и временные метки отдельных контактов остаются локальными данными.

## Воронка выбора и получения помощи

- `help_funnel.sql` извлекает только признаки и времена событий из проверенного production inbox: аккаунт 1, inbox 5, `nevidima_bot`. Ничего не изменяет. Известный тестовый диалог владельца и контакты с техническими тестовыми событиями исключаются целиком. Неизвестные тесты сотрудников автоматически не распознаются.
- `help_funnel.py` объединяет контакты, убирает повторы событий и строит агрегаты. Он не читает тексты диалогов и не обращается к сети.
- `reports/` содержит только агрегаты и пояснения. Снимок не является постоянным мониторингом и не обновляется сам.

### Повторение расчёта

Перед чтением production соблюсти guard из `AGENTS.md` и `docs/chatwoot-operations.md`: проверить VM через API, использовать доверенный SSH-ключ и PostgreSQL `verify-full` с CA провайдера. Выполнить SQL внутри `BEGIN READ ONLY`, с ограничением времени запроса. Пароль — только через защищённое окружение; не помещать его в аргументы или файлы отчётов.

На текущем Mac есть проверенный локальный транспорт `.runtime/timeweb_readonly_sql.py`, который сам выполняет эти проверки, read-only транзакцию и возвращает JSON-массив. Этот ignored helper не является частью переносимого набора аналитики: на другом checkout нужен утверждённый read-only доступ к PostgreSQL. Результат SQL сохранить закрыто в `analytics/private/` (каталог 0700, файл 0600), затем:

```sh
uv run python -m analytics.help_funnel analytics/private/features.json
uv run pytest tests/test_help_funnel.py -q --tb=short
```

### Определения и ограничения

Единица — уникальный Chatwoot contact, не число `/start`, нажатий, сообщений или заявок. Один контакт учитывается один раз за всю доступную историю. Хронология строгая: одинаковая временная метка не доказывает порядок событий. Сравнение не ограничено одним сеансом общения.

1. **H2:** хотя бы одно нажатие «Да, посмотреть» после `/start` / все контакты с `/start`. Событие — callback `continue` или точный входящий текст кнопки. Это получение клика, а не гарантия принятия устаревшего callback движком.
2. **H3 по заданной формуле:** подтверждённая отправка сертификата или отмеченная завершённая консультация после ответа на меню / контакты, ответившие на «Что сейчас важнее всего?» (`need:*`). Если запись исходящего меню есть, ответ должен быть позже неё. `menu_shown` означает именно запись в истории, а не подтверждённый показ на телефоне: для неё не требуется Telegram receipt. Это не доля просто выбравших карточку помощи (`aid:*`); последняя показана отдельно.

Сертификат подтверждается исходящим публичным PDF, совпадением имени файла и подписи с критериями существующего `scripts/backfill_certificate_history.py`, непустым Telegram `source_id` и отсутствием failed-статуса. Это доказательство принятой Telegram отправки, не прочтения или использования сертификата. Часть документов может не пройти строгий фильтр — это не означает, что их не выдавали.

Завершение консультации считается только по `scenario_requests.state=completed` с `completed_at` и `completed_message_id`. Заявка, назначение специалистки, её ответ, закрытый разговор и отправленный опрос не заменяют эту отметку. Встречи вне бота без отметки в этих данных неизвестны.

При импорте сохранены тексты, но отсутствуют callback metadata и receipts Telegram. Поэтому для legacy-когорты отсутствие события не означает отказ или неоказанную помощь. `native` — контакты без импортированных сообщений; это не срез всех событий после миграции. `imported` включает также последующие новые события этих контактов. SQL проверяет все сообщения выбранного inbox, но не пытается считать обещания/упоминания помощи доказательством её оказания.

`unknown` в JSON означает отсутствие подтверждающего наблюдения. Проценты относятся к наблюдаемым событиям: H3 нельзя выдавать за полную конверсию всей исторической базы. Для точной исторической H3 нужен отдельный реестр выдач и завершённых консультаций. При изменении схемы БД или канала сначала обновить и проверить SQL; пустой результат не считать нулевой активностью без проверки доступа и scope.
